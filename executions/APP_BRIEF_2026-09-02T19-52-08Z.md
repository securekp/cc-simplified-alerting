# Ally Monitoring App - App Brief

## App ID

`ally-monitoring` — display name **Ally Monitoring App**. Matches the existing scaffold's `package.json`; no rename needed.

## Problem & Vision

Cribl already has every ingredient for per-Source and per-Destination alerting: health status on every input and output, Insights throughput telemetry, and a Notification engine that fires on per-feed conditions. What's missing is a fast path from "here are my enabled Sources and Destinations" to "each one is watched."

Today an admin has to hand-author each alert in the Cribl UI, look up the right condition for every feed and direction, and repeat all of it every time a feed is added. It doesn't happen, so deployments run with no per-feed alerting at all.

This app auto-discovers what is actually enabled, shows what is already covered, and creates alerts from a template in a few clicks.

**One intent: is this feed still delivering data?** That is the failure the admin asked to be alerted on, and it is the only alert the app authors. A Source that has gone quiet and a Destination that cannot deliver are the same operational problem, so they get one coverage answer rather than two half-answers.

**Health is shown, not alerted on.** Every input and output reports `health` as `Green` / `Yellow` / `Red` / `Unknown`, aggregated across Worker Processes. All of it is surfaced in the coverage table — a Red Source is visible at a glance, and `status.error` gets its own indicator because a feed can be Green *and* carry an error. What the app does not do is author a separate health alert: the live catalogue offers no Source health condition, and the monitor mechanism copies only the shipped *throughput* queries, so expressing one would mean composing PromQL — which the app deliberately does not do (see Architectural Rule 2). Health in the table, plus one delivery alert per feed, is the scope.

**The vision in one line:** install to a meaningful set of alerts in one sitting, without first learning which condition IDs exist or what the Insights metric names look like.

## Target Users

**Cribl platform admins, exclusively.** They own the Stream deployment, configure the feeds, and are accountable for whether data still flows end to end. They have admin API access and can see all worker groups.

Ops / on-call engineers and data owners are *consumers* of the alerts, not users of the app — they receive them through whatever notification target the admin attaches and never need to open it. Baseline today is zero coverage and reactive discovery (someone downstream notices missing data and complains), so there is no import or migration path to build.

## Two Architectural Rules (read before writing any code)

### Rule 1: This is an authoring tool, never an evaluator

The app writes alert configuration to Cribl and never evaluates anything itself. The app runs in a sandboxed iframe with no background runtime — an app-owned alert engine would only evaluate while a browser tab was open, which is useless for alerting. Delegating to Cribl's engine means alerts keep firing when the app is closed or uninstalled, appear in Cribl's native UI and history, and reuse existing targets and silences.

**Non-negotiable:** no polling loops that check thresholds, no in-app rule engine, no timers that decide whether something is firing.

### Rule 2: Two mechanisms, both of them Cribl's — and no third

The app writes alerts two ways, and the admin chooses **per direction** in the bulk template. Both are objects Cribl's own UI creates; neither is an engine the app invented.

| | Mechanism A — Notification | Mechanism B — Insights monitor |
|---|---|---|
| Write | `POST /notifications`, `condition` from `GET /conditions` | `POST /m/{gid}/alert/monitors` **plus** a bridge `POST /notifications` |
| Where it shows up | Notifications, per worker group | the Insights alerts page, with a chart and an Activity trail |
| Per-feed by | `conf.name` | `rules[0].includedTags` (`type:id`) |
| Threshold from | the condition's own JSON Schema | `rules[].conditions[].condition.threshold` |
| Routed by | `targets` | notification **policies** (`mode: "policy"`) |
| Needs | the condition catalogue | a group whose monitor collection answers, and a shipped query to copy |

Mechanism A is the **default**, because it needs nothing but the condition catalogue and is therefore the route most likely to work on any given deployment. Mechanism B exists because A alone cannot satisfy the requirement it was asked to: an alert that appears where an Insights alert appears, with a chart and thresholds.

**Mechanism A payload** — `buildNotification` takes a feed plus a condition id and `conf`; nothing about it varies by direction:

```json
{
  "id": "ally-default-out_splunk",
  "condition": "unhealthy-dest",
  "group": "default",
  "targets": ["system_notifications"],
  "disabled": false,
  "conf": { "name": "out_splunk", "timeWindow": "60s", "notifyOnResolution": true }
}
```

The condition differs by direction; the shape does not:

| Direction | Condition | What it watches |
|---|---|---|
| Source | `no-data` (default), `low-volume`, `high-volume` | delivery volume |
| Destination | `unhealthy-dest` | feed health |

**Mechanism B payloads** — two writes, and the second is what makes the first deliver anything:

```json
{
  "id": "ally-default-ZscalerWeb",
  "name": "ZscalerWeb stopped delivering (default)",
  "description": "Created by the Ally Monitoring app. …using the query shipped with \"source_data_in_rate\".",
  "query": "sum(rate(total_in_bytes{namespace=\"\"}[5m])) by (input)",
  "enabled": true,
  "product": "stream",
  "params": {},
  "schedule_interval_seconds": 60,
  "firing_after": 300,
  "ok_after": 60,
  "isDefault": false,
  "rules": [
    {
      "name": "ZscalerWeb below threshold",
      "showOnChart": true,
      "includedTags": { "input": ["datagen:ZscalerWeb"] },
      "excludedTags": {},
      "conditions": [
        { "condition": { "type": "less_than", "threshold": 1 }, "enabled": true, "labels": { "severity": "critical" } }
      ]
    }
  ]
}
```

```json
{
  "id": "monitor-ally-default-ZscalerWeb",
  "condition": "monitor-alerts",
  "mode": "policy",
  "disabled": false,
  "targets": [],
  "templateTargetPairs": [],
  "conf": {}
}
```

Both mechanisms answer the one intent, and both feed **one coverage column**.

#### How the monitor route came back — and the four rules it came back with

An earlier revision specified a second engine, then dropped it because the monitor route had three unresolved problems: `/alert/monitors` returned an Express 404; `MonitorConf.rules[]` had no publishable schema (the spec resolves it to `Rule.conditions[].condition` → `Condition` → `$ref: Function`, the *pipeline function* schema — a generator collision, and the spec's own example ships `rules: []`); and both monitor engines reported `SERVICE_DOWN`.

A HAR capture of the org's **own Insights UI creating an alert** resolved the first two with direct evidence: the route exists under `/m/{gid}/`, and a real `rules[]` is in the capture. **The 404 was a prefix mistake, not a missing route** — the same trap as `/system/inputs`. The third is answered by construction rather than by a probe.

The rule that governed the removal still governs the return, and it is the one that matters: **never report success for an alert that cannot fire.** Four rules apply it, and none of them is optional:

1. **The host group is discovered by probing, and it is not the feed's group.** Monitors were observed in `default_search` while the feeds live in `default`. Preference goes to a group holding shipped `isDefault` Stream monitors — evidence its engine is wired up — then to any group that answers. If none answers, the mechanism is unavailable and names the path *and prefix* tried. `/m/{gid}/system-insights/healthcheck` is read before the capability is offered; `red` disables creation rather than reporting it as working.
2. **The PromQL query is copied verbatim from a shipped monitor, never composed.** Shipped queries use underscore metric names and an empty-string namespace matcher (`rate(total_in_bytes{namespace=""}[5m])`) the app cannot verify from inside a sandboxed iframe. A hand-authored expression matching no series is a monitor that never fires — the worst outcome available. No shipped monitor for that direction's throughput ⇒ the item is **blocked with a reason**, not improvised. A template whose query is not a throughput query is refused for the same reason: it would be created and then never counted as coverage.
3. **Per-feed scope lives in `includedTags`, not in the query.** `{input: ["datagen:ZscalerWeb"]}` — exactly the `type:id` values the metric join already builds, matched **exactly**, never by prefix. Only the feed tag is pinned: adding a `__worker_group` tag the deployment may not support would narrow the monitor to nothing, and a monitor that is silently too broad is far less dangerous than one that is silently dead.
4. **One rule, one enabled condition.** Every monitor Cribl ships carries `enabled: true` on the object and `enabled: false` on all three severity thresholds. So the coverage test has two parts — the object enabled **and** at least one condition enabled — and a created monitor carries exactly one threshold, which is the thing an admin can reason about and later tune.

#### The two mechanisms fail independently

`alerting` and `monitors` are separate capabilities with separate reasons to fail, and **each blocks only items of its own mechanism.** A monitor is *not* gated on `alerting`: `alerting` reflects whether the condition catalogue is readable, and a monitor's bridge uses the fixed `monitor-alerts` condition, which consults no catalogue. Whether the bridge write is permitted is only knowable by attempting it, so a bridge failure is reported per item as a **partial success** — the monitor exists and will fire on the Insights page, and nothing is delivered from it — never predicted by blocking the item up front.

#### Routing differs, and the app says so rather than papering over it

Mechanism A routes through notification **targets** (`GET /notification-targets`) — one ID space, one picker. Mechanism B routes through notification **policies**: the bridge carries `mode: "policy"` with empty `targets`, exactly as Cribl's UI writes it. **The app does not create policies**, so it states that a monitor's delivery is governed by the deployment's Insights policies and is not something this app configures.

Note also the **inverted `disabled` sense**: a Notification carries `disabled: true`, a monitor carries `enabled: false`. `createDisabled` sets both.

#### Conditions are discovered, never hardcoded

Call `GET /conditions?category=sources` and `?category=destinations`, paging to exhaustion. Each condition returns a JSON Schema for its `conf` fields — titles, descriptions, patterns, duration minimums — so **generate the configuration form from that schema**. A renamed or new condition in a future Cribl version then appears automatically instead of breaking the app. **Never fabricate a condition ID.** Hidden conditions are excluded unless `showHidden` is set — set it deliberately rather than by omission.

The full live catalogue (2026-09-02, `totalCount: 10`): `unhealthy-dest`, `backpressure-dest`, `persistent-queue-usage`, `low-volume`, `high-volume`, `no-data`, `persistent-queue-usage-source`, `search`, `license-expiration`, `monitor-alerts`. These names are for sanity-checking discovery output, not for hardcoding.

**Classify by what a condition watches, never by its `type`.** Six of the ten are `type: "metric"`, including `backpressure-dest` and both `persistent-queue-usage*`, which watch neither delivery volume nor feed health. A `type`-based rule files those as coverage and marks a feed watched for a delivery stop nobody is watching. Match on the id/name (`health`; `no-data|volume|byte|event|throughput|rate`) and return `unclassified` otherwise.

`Signal` (`health` | `volume` | `unclassified`) is a **label, not a routing decision.** It tells the admin which of the two a given alert watches; both count as coverage. `unclassified` alerts that attribute to a feed are still shown in its coverage cell — under "Also on this feed, but not watching for a delivery stop" — so nothing is hidden, but they never count. The moment `Signal` becomes a *requirement* ("this feed needs a health alert *and* a volume alert"), the asymmetric catalogue makes every feed fail it: Sources have no health condition and Destinations have no volume condition.

**`conf.name` is set from the feed and never from the template.** Every per-feed condition marks `name` required, and Cribl's own `uischema` pins it to `{"default": "${IO_ID}", "ui:disabled": true}`. It is applied last in `buildNotification` so a template-supplied `name` cannot point a whole bulk run at one feed.

**`conf` is per direction, and pruned.** The two directions land on different conditions declaring different fields, sometimes under shared names — `low-volume` has `dataVolume`, `unhealthy-dest` does not; `no-data` defaults `timeWindow` to `5m` while `unhealthy-dest` defaults it to `60s` with a 60s minimum. The two are configured, validated, stored, and pruned against their own schema independently. One shared `conf` bag sends a field the other condition never declared.

#### What Insights is still for

Throughput history from `POST /insights/metrics/query` drives the **sparkline column and nothing else.** **No Notification depends on a metric name**, so Insights being denied, disabled, unhealthy, or absent costs one column and cannot block a Mechanism A write. Hard rule in both directions: never gate a Notification on Insights, and never present the sparkline as if it were coverage.

A monitor does depend on Insights — that is what it is — but not on a metric *name the app chose*: it inherits the metric through the copied query. **Sparkline-Insights and monitor-Insights are separate capabilities on separate paths**, and either can fail without the other. The sparkline reads `POST /insights/metrics/query` (dot-separated names, unprefixed); the monitor mechanism reads `/m/{gid}/alert/monitors` and `/m/{gid}/system-insights/healthcheck`. Do not collapse them into one notice, and do not conclude from a dead sparkline that monitors are dead.

#### In the UI

The admin picks feeds and, per direction, a mechanism — and **the mechanism selector only appears when there is a choice.** If only one mechanism is usable there is no selector, and one notice says which one and why. If neither is, nothing is creatable and the table is a read-only coverage and health audit.

Never hide what was created. Every alert chip opens a configuration view built from the **stored object** as Cribl returned it, and the chip itself says which mechanism it is and qualifies itself when it is not real coverage: `(disabled)`, `(not routed)`, `(unmanaged)`, `(owner unknown)`. A Notification's `conf` fields are labelled from the condition's own schema, with undeclared keys listed rather than dropped. A monitor's fields are named in the component (no schema for one exists), and the three things that decide whether it can fire are all shown in full: the query, the feed tags, and each threshold with its own `enabled` state ("switched off — cannot fire"). Each view links out to where that object is edited in Cribl — the group's Notifications page, or the Insights alerts page — and states that this app creates alerts and never edits them.

## Implementation Rules Proven Against a Live Deployment

Verified empirically against a real Cribl Cloud org, not inferred from the spec. Each of these silently produces a wrong-looking table if ignored, so treat them as requirements.

1. **Health arrives inline with discovery.** `GET /m/:gid/system/inputs` and `/system/outputs` already return `status.health` as a string, plus a per-type `status.metrics` object and (Destinations) `status.error`. **One call per group per direction fills the whole coverage table on first paint.** `/system/status/*` is a lazy progressive enhancement, fetched only when a row expands for `healthCounts`.
2. **Join on `type` + `id`, and match exactly.** Metric dimension values are fully qualified `type:id` (`syslog:in_syslog:udp`, `splunk_hec:in_splunk_hec`, `cribl_lake:palo_traffic`) while config objects key on the bare `id`. **IDs can themselves contain colons and protocol suffixes** — `syslog:in_syslog:udp` is type `syslog`, id `in_syslog`, plus a `:udp` suffix. Construct `` `${type}:${id}` `` from the config object and compare for **exact equality**; never split the dimension value back apart, and never prefix-match (see rule 8). This now affects the sparkline only, not a write — but a wrong sparkline is still a wrong sparkline.
3. **Green does not mean fine.** Three Destinations were observed `"Green"` while carrying `status.error.message = "There is an issue with the underlying destinations."` Surface `status.error` as its own always-visible indicator so a Green-with-error feed is visibly not fine. Do **not** redefine health to compensate — that would put the app's verdict at odds with the Cribl UI's, the exact thing this design avoids. It is also one of the reasons health is a display column rather than an alerting intent: an alert on health alone would not fire for these three at all.
4. **`workerCount` is not a usable signal — do not consult it.** It read `0` for the `default` group while that group demonstrably had Workers running, and it is absent entirely on `defaultHybrid`. Parse it faithfully (`number | null`) and consult it nowhere: it must not block a write, must not be cited in a reason, and must not decorate a group label. A field that can be wrong must never be quoted at the admin as a fact.
5. **Filter groups on `type === 'stream'` in app code.** Asking for Stream groups returned `outpost`-type groups too. Do not trust the request parameter. Live: 10 groups — `stream` (2), `edge` (5), `search` (1), `outpost` (2).
6. **Filter feeds on `disabled !== true`.** Disabled feeds still report health (observed `disabled: true` with `"Green"`). Health is never the enabled test.
7. **A disabled alert is not coverage.** The one Notification on the verification org reports `disabled: true`. Counting an alert's existence rather than its enabled state marks a feed watched by something that cannot fire.
8. **One logical feed emits several metric series — summing them double-counts.** Observed: `subscription:palo_traffic_filtering` *and* `:test`, both `bytes = 3169258`; `subscription:zscaler_web_project` *and* `:zscaler`, both `84603299`; plus `syslog:in_syslog`, `:udp`, `:tcp`. Parent and `:suffix` children carry the **same** value, not complementary halves. Match the parent exactly; a `startsWith` join doubles or triples a feed's apparent throughput.
9. **There is a roll-up series with no `input` / `output` dimension**, equal to the ungrouped total. Exclude it, or the table gains an unnamed row and the count is off by one.
10. **The metric store contains far more feeds than the config calls, including internal plumbing.** `health.inputs` returned 47 series — among them `ServiceTcp:search`, `cribl:CriblLogs`, `http:http`, `router:engine_router` — against a config list of user feeds. **The config call is the spine and metrics are joined onto it, never the reverse.** Discard unmatched series silently; a configured feed with no series shows "no data," which is distinct from "not covered."
11. **Pack-scoped feeds have health and traffic but no row in the group config call.** The metric store returns `type:packName.feedId` values — `datagen:cribl-palo-alto-networks.palo_traffic` (33 MB/h), `open_telemetry:observeai.observeai-claudeDesktopOTLP`, `splunk_hec:cribl-crowdstrike-rest-io.out_splunk` — none of which appear in `/system/inputs|outputs`. **MVP excludes Pack feeds and the UI must say so on the coverage summary**, so a partial table is not read as a complete one. `/p/{pack}/system/inputs|outputs` and `includePacks` on `GET /notifications` are how a later version closes this.
12. **`status.health` can be absent entirely, not merely `Unknown`.** The synthetic `default` destination returned `status: {}` — no `health`, no `timestamp`, no `metrics`. Treat missing as `Unknown` and exclude it from the healthy tally; treating it as falsy-therefore-Green reports a feed healthy on no evidence. Also: `status.metrics` was `{}` on **every** destination while Sources returned populated per-type metrics — so per-type `status.metrics` is a Source-side signal.
13. **The throughput metric names are `total.in_bytes` / `total.out_bytes` / `total.in_events` / `total.out_events`.** Dot-separated, no `cribl.` prefix, no `_total` suffix. Queried live: `sum("total.in_bytes")` returned `217902914` over 1h, while **`sum("cribl.in_bytes_total")` and `sum("cribl.events_in_total")` — the names an earlier brief specified — matched no series at all.** The underscore form `total_in_events`, used by the `POST /alert/monitors` example in `openapi.json`, also matched nothing. **Discover names at runtime; the names here are for sanity-checking discovery output.** When a discovered name yields no series, say so visibly instead of drawing an empty sparkline. Never offer a health metric as a volume series — `health.inputs` reads `0`/`2`, not bytes.

### Facts retained from the monitor investigation

Live-verified. Some of these the monitor mechanism now depends on; the rest are kept so future work starts from evidence rather than repeating the probing.

* **`0` = Green, `2` = Red** in the metric store, cross-checked on three feeds across both directions whose `status.health` read `"Red"`. `1` (presumably Yellow) and the Unknown value were never observed, which is why the rule is **`health != 0`, never `health == 2`**. The same caution applies to the string form the app *does* use: `Unknown` and an absent `status` are "not known to be healthy", never "healthy".
* Series come from **`POST /system/metrics/query`**. `GET /system/metrics` is a different, GET-only endpoint; `POST /system/metrics/enum` enumerates dimension values. `max()` is the correct aggregation for health — the roll-up across all feeds also returned `2`, i.e. worst-state-wins.
* **Monitor PromQL uses underscore metric names and an empty-string namespace matcher** — `rate(total_in_bytes{namespace=""}[5m])` — which is *not* the dot-separated form `POST /insights/metrics/query` accepts. This is the single strongest reason the query is copied verbatim from a shipped monitor: two name conventions live in one product, and the app cannot verify from inside the browser which one the monitor engine resolves.
* **`openapi.json` is not evidence about this route.** `MonitorConf` there has no `type` / `detectionConfig` field and its `rules[]` has no usable schema, yet the live objects have well-formed `rules[]` — the spec was simply behind. So the deferral of percent-drop, anomaly, forecast, outlier, and change detection now rests on **not having captured a real monitor that does one**, not on the spec's silence. `MonitorType` and `ChangeConfig` belong to `AetosMonitorConf`, used only by `/products/lakehouse_engine_metrics/monitors` — a different endpoint, empty here and backed by a dead engine.
* A GET probe proves nothing about a POST-only route: Express answers `Cannot GET /path` for a path registered only for `POST`. Nothing can be concluded from the 404 sweep about `POST /system/metrics/query` or `POST /insights/metrics/query`.
* **A root 404 proves nothing about a group-prefixed route**, which is the mistake that cost the monitor mechanism a whole revision. `/alert/monitors` 404s at the root and answers under `/m/{gid}/`; `/system-insights/healthcheck` behaves the same way. Probe both forms before concluding a route is absent.

## Verify First, In Priority Order

Everything in the Implementation Rules above is settled. Two of the previously largest open items were closed by a HAR capture of the native Insights UI rather than by argument.

**Closed:** how a threshold is expressed in `MonitorConf.rules[]` (`rules[].conditions[].condition = {type, threshold}`, with `enabled` and `labels.severity` alongside — captured live); how a monitor is scoped to a feed (`rules[].includedTags = {input|output: ["type:id"]}`); how monitor output reaches the Insights alerts page (the `monitor-{id}` bridge Notification on `condition: "monitor-alerts"`, `mode: "policy"`); and which conditions the deployment offers per direction (`unhealthy-dest` for Destinations, volume conditions for Sources, nothing health-shaped for Sources).

**Still open:**

1. **Whether the discovered Insights metric names are queryable through `POST /insights/metrics/query`** under the same names the catalogue reports, given that neither `cribl.in_bytes_total` nor the underscore form matched any series (Implementation Rule 13). Blocks the sparkline column only — no Notification depends on a metric name, and a monitor inherits its metric through the copied query rather than a name the app chose. There is an actionable half to this: **`src/api/insights.ts` still calls the catalogue at the root, where it 404s.** The group-prefixed form answers, but it returns underscore-form names while the query endpoint takes dot-separated ones, so fixing the prefix means reconciling the two name conventions — probe both live before changing either.
2. **Whether a monitor created here actually evaluates.** The host group is chosen as the one that answers *and* holds Cribl's shipped Stream monitors, and `/m/{gid}/system-insights/healthcheck` is read before the capability is offered — but the `SERVICE_DOWN_aetos` message that killed the earlier revision was only ever seen at the root and was never re-probed at the group prefix. The honest position, and the one the UI must hold to: the app can create the object Cribl's own UI creates, in the group Cribl keeps them in, and **cannot prove from inside a browser that the evaluator is running.** Nothing in the UI may claim otherwise — an unreadable healthcheck leaves monitors creatable with an explicit "cannot confirm anything will evaluate them", never a silent success.
3. **`POST /m/{gid}/alert/monitors` for a genuinely new id.** The capture only ever shows the Insights UI `PATCH`ing an id that already existed, so create is the one verb here that is not directly proven. The app POSTs first and falls back to PATCH **only** when the rejection says the object exists (409, or 400 naming existence); any other rejection is reported as-is, because a blind PATCH after a denied POST could overwrite an object the app did not create.
4. **Whether a deployment with no notification policy delivers monitor output anywhere.** The bridge Notification is copied field for field, empty `targets` included, because monitor alerts route through policies and this app creates no policies. The alert appears and fires on the Insights alerts page either way; whether it reaches a human is a deployment setting the UI states rather than assumes.
5. **The exact per-alert URL in the Cribl UI.** The configuration view renders the stored object inline and links to the owning group's Notifications page or `/insights/alerts/activity`, both known-good. A per-object deep link would be a small improvement; no such route is documented or confirmed, and one is never guessed.

## Key Workflows

### Workflow 1: Review Alert Coverage (landing view) — MVP

- **User sees**: One dense table per direction, covering every enabled Source and Destination across accessible Stream worker groups. Columns: name, type, group, current health, a separate error indicator, recent throughput sparkline, and **one coverage column** answering "is anything watching this feed for a delivery stop?" A header coverage summary ("34 of 51 feeds covered, 2 unhealthy"). An unhealthy feed with nothing watching it is styled as the most important row in the app.
- **User does**: Sorts, searches, and filters to find the gaps — by group, by direction, "no alerts yet," "currently unhealthy," "has an error." Expands a health cell to see the per-Worker-Process breakdown.
- **Result**: Nothing is written. This is a read-only audit that answers "what is flowing, is it healthy, and what is watched?"
- **Permissions**: Renders whatever the API returns for the signed-in user. No app-level filtering — Cribl RBAC and worker-group ACLs are the single source of truth. An admin with access to two of five groups sees two groups' worth of feeds, presented as normal rather than as an error.

Load sequence: list groups (`GET /master/groups`, filtered to `type === 'stream'`) → per group fetch inputs and outputs (health inline, filter `disabled !== true`) → discover conditions per direction → **locate the monitor host** (probe `/m/{gid}/alert/monitors` across candidate groups, pick the one holding Cribl's shipped Stream monitors, then check that group's Insights engine) → read the Insights metric catalogue for the sparkline → fetch existing Notifications and the host group's monitors, **both paged to exhaustion**, and attribute them back to feeds → reconcile the KV registry → render. Sparklines (batched one query per group per direction) and `healthCounts` load after first paint.

Both mechanisms feed **the same coverage column**, because the admin's question is about the feed, not the machinery: a Notification and a monitor on one feed are two chips in one cell, each labelled with its mechanism. The three tests are applied identically to both — enabled, `health`-or-`volume` signal, attributable to exactly one feed — so nothing counts as coverage that cannot fire.

### Workflow 2: Bulk-Create Alerts From a Template — MVP, the primary value workflow

- **User sees**: A sticky action bar once rows are selected ("N selected — Create alerts"), opening a side drawer: per-direction **mechanism** → that mechanism's settings → routing → **preview** → confirm.
- **User does**: Multi-selects rows (with "select all uncovered" as a shortcut); for each direction in the selection, picks a mechanism **only where both are usable**, then fills its settings. A Notification's fields are **generated from the condition's JSON Schema, including duration minimums, so an invalid value cannot be offered**; a monitor's are the threshold, comparison, severity, and the sustained windows (`firing_after` / `ok_after`), with the shipped monitor whose query is being copied named on screen. Attaches notification targets, or opts to create everything disabled for now.
- **Result**: After an explicit confirmation, sequential writes with progress feedback — **one `POST /notifications` for Mechanism A, and for Mechanism B a `POST /m/{host}/alert/monitors` followed by its bridge `POST /notifications`**. Per-item success and failure reported honestly, including the objects as created. Coverage table refreshes and newly covered rows flip. Each created alert is registered in KV and links out to the native Cribl UI.
- **Permissions**: Mechanism A requires write access to `/notifications`; Mechanism B requires it on `/m/{host}/alert/monitors` **and** `/notifications`. Each denial blocks only its own mechanism, with the payload still shown so the admin sees exactly what is gated.

**The preview step is mandatory and cannot be skipped.** It lists one row per selected feed, stating the mechanism, **every object that will be written** — for a monitor, both the monitor and its bridge — and, for any feed already watched or with no usable mechanism, the reason, so every selected feed is accounted for and no count goes unexplained. Nothing is created before the admin confirms. Partial failure is expected and must not be hidden — failed items stay selected so they can be retried without redoing the configuration.

**Partial success is a first-class outcome here, not an error path.** A monitor written whose bridge Notification failed is reported as `partial`: "created, not routed" — it will appear and evaluate on the Insights alerts page but deliver nowhere until routing is attached. The same honesty applies to the registry: an alert created whose KV entry did not save says both things.

### Workflow 3: Inspect a Created Alert — MVP

- **User sees**: Clicking an alert chip in a row's coverage cell opens its configuration: the **stored object as Cribl returned it**, the feed watched, the worker group, the signal, and the routing (saying so explicitly when there is none). A Notification shows its condition with each `conf` field labelled from that condition's own schema. A monitor shows the host group it lives in, its query, its feed tags, and **each threshold with its own `enabled` state**, because a monitor whose only condition is switched off cannot fire and must not read as coverage.
- **User does**: Reads it, and follows the link out for any change — the group's Notifications page for a Notification, the Insights alerts page for a monitor.
- **Result**: Read-only. Answers "what is this alert actually configured to do?" — the question that follows immediately after creating one.
- **Detail that matters**: it renders the *stored* object, not the template, so an alert edited in Cribl afterwards shows its real settings. Fields the schema does not declare are listed at the bottom rather than hidden — an unrecognised key on a live alert is exactly the thing worth seeing. A condition missing from the catalogue is called out, with its settings under raw field names. A monitor with no bridge Notification carries a warning that it is not routed. The view states that this app creates alerts and never edits them.
- **Ownership is claimed from evidence, in a fixed order.** A KV registry entry is proof; failing that, an id in the app's reserved `ally-` namespace is strong enough to claim authorship; only with a **readable** registry and neither of those does the view say "not created by this app". If the registry could not be read at all it says ownership is unknown — the earlier build collapsed that case into a denial and labelled the app's own alerts as somebody else's.

### Workflow 4: Tune an Individual Alert — deferred (highest-value deferred item)

- **User sees**: An editor for one alert, generated from the condition schema, alongside recent Insights history versus the configured threshold so the admin can see whether it would have fired against real traffic.
- **User does**: Adjusts settings and saves, or disables rather than deletes.
- **Result**: A confirmed overwrite of the underlying object, naming it explicitly. Outcome reported.
- **Permissions**: Applies only to alerts this app manages, so the app never silently overwrites something a human hand-built. Delete requires an explicit confirmation naming the object and stating the action cannot be undone. Note this needs `PATCH` / `DELETE` on `/notifications/*`, which `config/policies.yml` deliberately does not grant today. `PATCH` on `/m/:gid/alert/monitors/*` *is* granted, but **only** as the id-already-exists recovery inside create — it is not an editing affordance, and turning it into one is this workflow's job, behind the same ownership check.

### Workflow 5: Re-Scan for Coverage Drift — deferred

- **User sees**: A banner on return — "N new Sources and M new Destinations have no alerts."
- **User does**: Selects the new items and runs Workflow 2 against them, reusing the last-used template settings from KV.
- **Result**: Coverage keeps pace with a deployment that keeps growing.
- **Permissions**: Same as Workflow 2.

### Workflow 6: Verify Alerts Are Working — deferred

- **User sees**: An alert-activity view — which alerts have fired, how often, and which have never fired.
- **User does**: Spots noisy alerts and suspiciously silent ones, then jumps to Workflow 4 to retune.
- **Result**: Read-only. Closes the loop so the admin trusts what they built.
- **Permissions**: Requires read access to `/alert/history`, which 404s at the root. **Re-probe it under `/m/{gid}/` before concluding it is absent** — that is exactly the mistake that hid `/alert/monitors` for a whole revision. Monitors partly cover this workflow already, for free: an alert created as a monitor gets a chart and an Activity trail on the Insights alerts page, which is where the app links.

## Data & Actions

**The app will fetch from Cribl:**

- **Stream worker groups** — `GET /master/groups`. Scopes discovery and labels rows (Workflow 1). Filter to `type === 'stream'` in app code; do not consult `workerCount`.
- **Enabled Sources and Destinations, with health inline** — `GET /m/:gid/system/inputs`, `GET /m/:gid/system/outputs`. Name, ID, `type`, `disabled`, `status.health`, per-type `status.metrics`, and (Destinations) `status.error`. The backbone of Workflow 1; filter `disabled !== true`, treat a missing `status.health` as `Unknown`.
- **Per-Worker-Process health detail** — `GET /m/:gid/system/status/inputs`, `/system/status/outputs`. Adds `healthCounts` per state and `pq` queue status. Fetched lazily on health-cell expand only.
- **Notification conditions and their schemas** — `GET /conditions?category=sources`, `?category=destinations`, `GET /conditions/{id}`. Drives the schema-generated settings form (Workflow 2), the direction of an existing alert (via a condition's `category`), and the field labels in the configuration view (Workflow 3). Never hardcode IDs or field names. Paginated; hidden conditions excluded unless `showHidden` is set.
- **Throughput history from Insights** — `POST /insights/metrics/query`, **for the sparkline column only**. Metric expressions over names **discovered at runtime**; on the verification org those were `total.in_bytes`, `total.in_events`, `total.out_bytes`, `total.out_events` (Implementation Rule 13). Sent with `dimensionFilters` including `{name: "namespace", operator: "eq", value: "data_insights"}` plus the group, and `dimensionSplits` on the per-feed dimension.
  - **Batch, do not fan out:** one query per group per direction with `dimensionSplits`, not one per row. Dozens of feeds against a 30-second proxy timeout makes per-row querying a guaranteed timeout.
  - Apply Implementation Rules 2 and 8–11 when reading results: exact-match the dimension value, skip `:suffix` children, skip the undimensioned roll-up, discard unmatched series.
- **Insights metric catalog** — `GET /system-insights/metrics` for names, `GET /system-insights/metrics/{id}` for label names and values. **The per-feed dimension label is discovered here at runtime, not hardcoded.** Returns 404 on the verification org, which costs the sparkline and nothing else.
- **Insights health and settings** — `GET /system-insights/healthcheck` (at the root, for the sparkline) and `GET /system/settings/insights`. Lets the app explain a blank chart instead of rendering one.
- **Insights monitors** — `GET /m/:gid/alert/monitors`, `GET /m/:gid/alert/monitors/{id}`. Three jobs in one collection read: it **locates the host group** (the route 404s where no collection lives, so answering *is* the discovery), it supplies the **shipped `isDefault` Stream monitors whose query the app copies**, and it returns the existing monitors that are attributed back to feeds for the coverage column. Paged to exhaustion like every other list endpoint.
- **The monitor host's Insights engine** — `GET /m/:gid/system-insights/healthcheck`, asked of the **host group**, returning `{"items":[{"status":"green","reported_at":…}]}`. This is the one health read that gates a write: a monitor written where nothing evaluates it is a silent failure, and `red` therefore disables monitor creation rather than reporting it as working. A healthcheck that cannot be read leaves monitors creatable with an explicit "cannot confirm anything will evaluate them" notice — degraded, but never a false claim of success.
- **Existing alerts** — `GET /notifications` (accepts a **`groupId`** filter and an `includePacks` flag). Attributed back to the feed each targets to compute the coverage column and reconcile the registry. **See "Attributing existing alerts back to feeds" below — this is not a trivial lookup.**
- **Notification targets** — `GET /notification-targets`, to populate the routing picker. Verified present, returning `system_email` (smtp) and `system_notifications` (bulletin_message). `GET /notifications` is the alert-object list and **must not** be used to populate a routing picker.

**No root-level service-health read.** An earlier revision queried `GET /health` and `GET /system/messages` to detect a dead monitor engine from `SERVICE_DOWN_*` messages. Monitors are back and the engine gate is back with them, but it is asked of the **host group's own Insights healthcheck** — the service that would actually evaluate the monitor — rather than inferred from a deployment-wide message list. Neither `/health` nor `/system/messages` is declared in `config/policies.yml`. Everything else the app depends on announces its own failure at the point of use.

**Page every list endpoint to exhaustion.** `GET /notifications`, `GET /conditions`, `GET /notification-targets`, and `GET /m/:gid/alert/monitors` all take `offset` / `limit` and return paginated envelopes. Reading only the first page makes existing alerts invisible, which renders covered feeds as **uncovered** — and on the monitor collection it would also hide the shipped monitor the app needs a query from, silently costing the whole mechanism.

**`limit` and `offset` are all-or-nothing.** Verified live: `?limit=200` without `offset` is rejected by every list endpoint with `{"status":"error","message":"missing 'offset' parameter, 'offset' is required when 'limit' is provided"}`. The error body has **no `items` key**, so `body.items ?? []` would read it as "nothing configured" and invert the whole coverage table. The paginator builds `{ ...query, offset, limit }` in a single object so the pair cannot be split, and `assertPaginated` rejects any envelope without `items` instead of defaulting it. The same `{status, message}` envelope is the platform's general error shape.

**Endpoint availability is discovered, not assumed — and a root 404 is not an absent route.** On the verification org `/alert/monitors`, `/alert/history`, `/system-insights/metrics` and `/system-insights/healthcheck` all return Express 404s **at the root**, while `/conditions`, `/notifications`, `/notification-targets` and `/system/settings/insights` answer there. An earlier revision read that 404 sweep as proof the monitor route did not exist and deleted the mechanism; a HAR capture of the native Insights UI then showed it answering perfectly well under `/m/{gid}/`. So: **probe the group-prefixed form too**, treat every new path as a hypothesis until it answers, and name the specific path when degrading. Monitor host discovery is this rule implemented as code — the app does not ask which group hosts monitors, it asks each group and believes whichever one answers.

**Attributing existing alerts back to feeds.** This must work for alerts the app did not create, and it now runs over two collections, so anything it gets wrong lands directly in the one coverage column:

- **Notifications:** `conf.name` holds the **bare feed ID** — no `type`, no direction. A Source and a Destination sharing an ID are indistinguishable from `conf.name` alone. Resolve direction from the **condition's `category`** (`sources` vs `destinations`) in the discovered catalogue, and scope by the Notification's `group`. Match on `(group, direction, id)`.
  - **A Notification with no `group` whose name matches feeds in more than one group is genuinely ambiguous, and is reported as unattributed.** `group` is optional on the object, so this is a real state, not a malformed one. Counting it toward both feeds would mark two feeds watched by one alert; picking either would be a guess. The reason names the count — "`in_syslog` is a source in 2 groups and the alert names none" — so the admin can add the group in Cribl and have it attribute on the next load.
- **Monitors:** scope comes from `rules[].includedTags` as fully qualified `type:id` values, so the join is **the same exact-equality match the metric join uses** — never a prefix match, never a parse of the tag apart (Implementation Rules 2 and 8 apply verbatim). One monitor may legitimately scope several feeds — Cribl's own `source_data_in_rate` does — so it appears on every row it actually watches. A monitor with **no** feed tag watches the whole deployment: a real and useful monitor, but not per-feed coverage, so it is reported as unattributed rather than spread across every row.
- **Cribl's ~38 shipped `isDefault` monitors are skipped entirely.** They are deployment-wide, not per-feed, and listing them against every row would bury the coverage this app exists to show.
- **Only an enabled alert on a `health` or `volume` signal counts as coverage.** `unclassified` attributes to the feed and appears in its cell, never as coverage. For a monitor "enabled" is **two** tests, not one: the object's `enabled` **and** at least one rule condition's `enabled` — every shipped monitor is `enabled: true` with all three thresholds `enabled: false`, so testing only the object would mark most feeds watched by something that cannot fire.
- **A monitor's signal is read from its query, and narrowly.** Only a throughput metric (`in_bytes`/`out_bytes`/`in_events`/`out_events`) counts as watching for a delivery stop. `pq_buffered_events` and `blocked_outputs` are good monitors containing volume-ish words, and neither detects a feed that went quiet — the same reason `persistent-queue-usage` is `unclassified` on the Notification side.
- **The `monitor-{id}` bridge is recognised, not reported.** `{id: "monitor-x", condition: "monitor-alerts", conf: {}}` carries no `conf.name` and belongs to no feed, so calling it unattributed would be technically true and useless — it is not an alert, it is the routing half of one. Bridges are set aside into their own map and consumed by monitor attribution to answer "does this monitor deliver anywhere?" The org's one pre-existing Notification is exactly this object.
- **Never guess.** Anything that cannot be attributed to exactly one feed is listed as unattributed with its reason, not silently dropped and not counted twice.
- **Tolerate unknown fields.** Real objects carry `mode: "policy"` and `templateTargetPairs: []`, neither documented. The read model accepts them, and the write path emits them **only** on the bridge, where they were captured. The same tolerance is what lets the configuration view render an unrecognised key rather than hide it.

**The app will create in Cribl:**

- **Notifications** — `POST /notifications`, one per feed, on a discovered condition with `conf.name` set to the feed ID (Mechanism A).
- **Insights monitors** — `POST /m/{host}/alert/monitors`, one per feed, plus its bridge `POST /notifications` (Mechanism B). Two writes, reported as one item with a `partial` outcome available.
- **Creates nothing else.** No Sources, Destinations, pipelines, routes, notification targets, notification policies, or Insights settings — and **no third mechanism.** Two Cribl objects, both of them Cribl's own.

### Write payloads — build exactly these shapes

**Mechanism A — `POST /notifications`.** Required by the schema: only `id` and `condition`. The app sets six fields:

```json
{
  "id": "ally-default-out_splunk",
  "condition": "unhealthy-dest",
  "group": "default",
  "targets": ["system_notifications"],
  "disabled": false,
  "conf": { "name": "out_splunk", "timeWindow": "60s", "notifyOnResolution": true }
}
```

The same builder produces a Source alert; only `condition` and `conf` differ:

```json
{
  "id": "ally-default-in_splunk_hec",
  "condition": "low-volume",
  "group": "default",
  "targets": ["system_notifications"],
  "disabled": false,
  "conf": { "name": "in_splunk_hec", "dataVolume": 1024, "timeWindow": "60s", "notifyOnResolution": true }
}
```

Rules on this payload:

- **`conf` field names and constraints come from the discovered condition's JSON Schema**, not from these examples, and are **pruned against it** — `low-volume` declares `dataVolume`, which `unhealthy-dest` does not.
- **`conf.name` is applied last**, from the feed. A template-supplied `name` must not be able to point every alert in a bulk run at one feed.
- **`id` is sanitized.** Feed IDs allow characters object IDs do not (colons, dots, slashes): `ally-${group}-${id}` with non-`[A-Za-z0-9_-]` runs collapsed to `_`, edges trimmed, capped at 100 chars.
- **`group` scopes the alert** — a plain field on create, and `groupId` as the query parameter on read-back. No label filter to smuggle it into.
- **`targets` takes notification *target* IDs** from `GET /notification-targets`. One ID space, one picker; the app creates no targets.
- **Creating disabled is `disabled: true`.**

**Mechanism B — `POST /m/{host}/alert/monitors` then `POST /notifications`.** Both shapes are given in full under Architectural Rule 2 above. Rules on them:

- **The `query` is copied verbatim** from a shipped `isDefault` `product: 'stream'` monitor, along with its `params`. Never composed, never edited, never string-interpolated. Monitor PromQL uses underscore metric names and an empty-string namespace matcher that the app cannot verify from the browser, and hand-authored PromQL that resolves to nothing yields a monitor that never fires — the worst possible outcome for an alerting tool. **No template for a direction means no monitor for that direction**, stated plainly.
- **Scope goes in `rules[0].includedTags`, never in the query** — `{input: ["datagen:ZscalerWeb"]}`, exactly the `type:id` tag the metric join already builds. Only the feed tag is pinned: adding a `__worker_group` tag this deployment may not support would narrow the monitor to nothing, and a monitor that is silently too broad is far less dangerous than one that is silently dead. Where the same feed id exists in another group, the UI says so.
- **Exactly one rule with exactly one enabled condition.** Shipped monitors stack three severities on one rule; this app creates alerts for one intent, and a single threshold is the thing an admin can reason about and later tune. `enabled: true` on the condition is mandatory — the shipped default is `false`.
- **`less_than`, not `greater_than`.** The one place the app inverts the shipped monitors, which all watch for a spike: "stopped delivering" is a floor.
- **`isDefault` is never `true`.** That flag marks the monitors Cribl ships, and claiming it would hide an app-created object among the defaults an admin is told not to delete.
- **`id` uses the same `ally-` namespace and the same sanitizer** as a Notification, so ownership is recognisable from the id alone. The two mechanisms therefore produce the *same* id for a feed — fine in Cribl, because the objects live in different collections, and handled in KV by keying on the mechanism.
- **`firing_after` / `ok_after` are the anti-flap window**, defaulted from the copied template (300 s / 60 s live) rather than invented.
- **The bridge is copied field for field**, `mode: "policy"`, `templateTargetPairs: []` and empty `targets` included. That is not an oversight in the capture: monitor alerts route through notification **policies**, and this app creates no policies. The UI states this rather than implying delivery.
- **The disabled sense is inverted between the two objects** — a Notification takes `disabled: true`, a monitor takes `enabled: false`. "Create disabled" sets both, and getting one wrong ships an alert the admin believes is off.
- **`PATCH` is a recovery, not an edit.** It is attempted only when `POST` is rejected because the id already exists (409, or 400 naming existence). Any other rejection is reported as-is — a blind PATCH after a denied POST could overwrite an object this app did not create.

**The app never modifies** Sources, Destinations, pipelines, routes, notification targets, notification policies, or Insights settings. It reads platform configuration and writes only alerting configuration. Insights settings are read to *explain* a problem, never written to fix one. **Nothing is ever deleted**, including its own objects: `/notifications/*` is granted GET-only, which is why Workflow 4 is deferred rather than partially built, and the monitor `PATCH` grant exists solely for the id-collision recovery above.

**The app will remember (general state):**

All persistence uses the **app-scoped KV store** (`CRIBL_API_URL + '/kvstore/...'`). Values are written as serialized strings per the Cribl Apps guidance; reads accept both a string and a raw object, because a value written by an earlier build is still out there.

- **Managed-alert registry** — `ally-monitoring/managed/{notification|monitor}/{id}`. One record per alert the app created: ID, worker group, feed ID, direction, signal, the settings used, and — for a monitor — the host group it was written to, the template its query was copied from, and its bridge's id. It distinguishes app-managed from hand-built so the app never claims ownership of something it did not create.
  - **The record does not store whether the bridge write succeeded, deliberately.** Whether a monitor is routed is read live: the bridge is either in `GET /notifications` on the next load or it is not, and `routed` is derived from that. A cached "routed" flag could only ever disagree with the platform — stale in the direction that matters, since an admin who attaches routing by hand afterwards would still be told the alert delivers nowhere. The bridge *id* is stored because it is what the live read is looked up by.
  - **The path segment is the mechanism, and it has to be.** The two mechanisms deliberately produce the same id for a feed, so a single KV path would have a monitor record overwrite the Notification record and the app would forget which mechanism it used and where. `loadRegistry` lists **both** prefixes and fails the whole read if either listing fails — a half-listed registry would silently report the app's own alerts as unmanaged. `notification` is unchanged, so records written before monitors existed still read back; no migration is performed.
  - **This is a cache, not the truth.** On load, reconcile per mechanism: drop entries whose object no longer exists in the collection it belongs to, and count unregistered alerts toward coverage as "unmanaged." **A stale entry must never make an uncovered feed look covered.** If no monitor host was found, monitor entries are left alone rather than judged — absence of a host is absence of evidence, not proof the monitor is gone.
- **Last-used template settings** — `ally-monitoring/template-defaults`: `sourceConditionId`, `sourceConf`, `destinationConditionId`, `destinationConf`, `notificationTargets`, plus `sourceMechanism` / `destinationMechanism` and `sourceMonitor` / `destinationMonitor` thresholds. Stored **per direction** because the two directions land on different conditions with different `conf` fields *and* may land on different mechanisms — a shared blob would carry a field the other side does not declare. Stored monitor settings are **coerced field by field on read**, never trusted straight into a write payload: they came from a store an earlier version wrote, so an unrecognised value falls back to the current default. App-scoped, so the whole admin team applies consistent windows and thresholds and the recurring "new feeds appeared, cover them the same way" pass is near-one-click.

**User-specific settings (stored per user):**

**None** — deliberately. View preferences (selected group, filters, sort order) live in component state and the URL only, never in KV. Every admin sees the same deployment-wide coverage picture on open, which is the right default for a shared operational tool: a remembered filter is exactly how someone misses an uncovered source.

**Secure secrets:**

**None.** The app makes no external calls and holds no third-party credentials. Cribl API authentication is injected by the platform's fetch proxy — the app never sees a token. Alert delivery credentials belong to the notification targets the app references by ID.

## UI Structure

### Overall Layout

**Table-first with a bulk-apply drawer.** One dense coverage table is the home screen and the entire product surface for MVP. Selecting rows opens a side drawer to configure, preview, and confirm — **no page navigation between finding the gaps and fixing them.**

Rationale: the admin's job is a sweep across dozens of feeds. A wizard optimises for one careful item at a time and would make the real task tedious; a dashboard optimises for looking rather than doing. The table keeps the gap list and the fix in one view, and the drawer keeps context visible while configuring.

### Key Screens/Pages

1. **Coverage table (home)** — Header: worker-group selector, direction filter, "uncovered only" / "unhealthy only" / "has an error" filters, free-text search, coverage summary. Sources and Destinations render as separate sections under their own headings. Each row: selection checkbox, name, type, group, a health cell that expands to lazily load per-Worker-Process `healthCounts`, an always-visible `status.error` indicator, a throughput sparkline, and **one coverage column** holding clickable alert chips from **either** mechanism. A chip states its mechanism and qualifies itself when it is not real coverage — `(disabled)`, `(not routed)`, `(unmanaged)`, `(owner unknown)` — because a chip that looks like coverage and cannot fire is the one lie this table must not tell. Sticky action bar when rows are selected.
2. **Bulk-apply drawer** — Steps: per-direction **mechanism** → that mechanism's settings (a Notification's rendered from the condition schema; a monitor's threshold, comparison, severity and windows, naming the shipped monitor whose query is copied) → routing → **preview list** → confirm. The mechanism step appears only where there is a choice. Preview is not skippable and shows **every object** that will be written, both halves of a monitor included. Inline per-item outcomes after apply, with `partial` as a distinct outcome and failures retryable and still selected.
3. **Alert configuration view** *(Workflow 3)* — opened by clicking an alert chip, and built per mechanism from the stored object. A Notification: schema-derived labels, undeclared fields at the bottom, a link to the group's Notifications page. A monitor: host group, query, feed tags, and each threshold with its own `enabled` state, a warning if it has no bridge, and a link to `/insights/alerts/activity`. Both state that this app creates alerts and never edits them.
4. **Per-alert tuning editor** *(deferred, Workflow 4)* and **alert activity view** *(deferred, Workflow 6)*.

Routing uses React Router with `basename={window.CRIBL_BASE_PATH}`. Filter and group selections live in the URL so a view can be shared or reloaded.

### Look / Feel

**Capra design system** (`@capra/core`, `@capra/icons`, `@capra/theme`), already in the scaffold — see https://capra.cribl.io/llms.txt. The app should look like a native part of the Cribl UI, not a bolted-on tool.

- Use Capra design tokens in CSS via the custom `token()` function — **never a raw CSS variable**.
- **Validate every token name against `@capra/theme`'s type declarations before using it.** The postcss plugin passes an unknown token through as invalid CSS and the browser silently drops the declaration — no build error, just a missing layout rule. Live bites: `spacing.xxs` and `radius.sm` do not exist (spacing is `none|xs|sm|md|lg|xl|2xl`; radius is `md|lg|xl|full`). Confirm by grepping the built CSS for a leftover `token(`.
- **Do not apply CSS classes to Capra components**; handle spacing with wrapper elements outside them.
- **Do not write selectors that depend on Capra internals, class names, or DOM structure.**
- Component gotchas found the hard way: `Text` has no `-bold` variants (use `body-sm-semibold`); there is no `Heading` export; `Pill` children are typed `ReactNode & string`, so wrap a number in `String()`.
- Dense, scannable table styling — this is an operational audit view, not a marketing page.
- Health uses Capra's semantic status tokens so `Green` / `Yellow` / `Red` / `Unknown` read correctly in both themes and match how health is coloured elsewhere in Cribl.
- Coverage state carries clear visual weight: **an unhealthy feed with nothing watching it should be the first thing the eye lands on**, and uncovered feeds should stand out from covered ones.
- An alert chip is a real button, because it opens the configuration view. Strip the button back to nothing so the Capra `Tag` inside keeps its own look — the affordance comes from the cursor and the focus ring, not a second border.

## Permissions & Access

- **Who can use this app?**: Cribl platform admins. Whoever an admin shares the app with, subject to the paths declared in `config/policies.yml`.
- **No app-level filtering**: the app renders whatever the Cribl API returns for the signed-in user. Cribl's RBAC and worker-group ACLs are the single source of truth. The app adds no parallel authorization logic — a second access model would drift from the platform's and give a false impression of what a user can see.
- **Permission-aware behavior**: every capability fails independently and names both the missing permission and what the user can still do. Never a generic error, never an empty screen. See Edge Cases.

Declare every Cribl API path the app calls in `config/policies.yml`, **including the `/m/:gid/...` variants**. Note that `openapi.json` contains **no `/m/{gid}/...` paths at all** — the group prefix is a leader-side convention layered over the flat paths, so it must be declared explicitly rather than inferred from the spec. The full set: `/master/groups`, `/m/:gid/system/inputs`, `/m/:gid/system/outputs`, `/m/:gid/system/status/inputs`, `/m/:gid/system/status/outputs`, `/conditions`, `/conditions/*`, `/system-insights/metrics`, `/system-insights/metrics/*`, `/system-insights/healthcheck`, `/m/:gid/system-insights/healthcheck`, `/system/settings/insights`, `/insights/metrics/query` (POST), `/notifications` (GET, POST), `/notifications/*` (GET), `/notification-targets`, `/m/:gid/alert/monitors` (GET, POST), `/m/:gid/alert/monitors/*` (GET, PATCH). KV paths (`/a/{appId}/kvstore/*`) are granted automatically by the AppUser role and are deliberately not redeclared.

**The monitor grant is group-prefixed only**, because that is the only prefix at which the route exists. `PATCH` on the item path is granted for the id-already-exists recovery — the only verb proven there by the capture — and `DELETE` is granted nowhere, on either collection. `/health` and `/system/messages` were declared by an earlier revision and stay removed: the engine gate now reads the host group's own Insights healthcheck, so an app should not hold read access to a deployment-wide service it does not consult.

## External Integrations (if any)

**None.** Every call goes through the Cribl API. `config/proxies.yml` stays empty, there is nothing external for an admin to approve at install time, and the app holds no third-party credentials.

Alert delivery is the platform's job: the app attaches an existing notification target to each alert it creates and Cribl handles Slack, email, or PagerDuty delivery. **The app never sends a notification itself.**

## MVP Scope

**Must-have:**

- Discover Stream worker groups, filtering to `type === 'stream'` in app code and consulting `workerCount` nowhere.
- Discover Sources and Destinations per group with health inline, filtering out `disabled === true`, treating a **missing** `status.health` as `Unknown` rather than healthy.
- Correctly join config objects to metric dimension values: construct `` `${type}:${id}` `` and match **exactly** — no prefix matching, no splitting the dimension value apart, skip `:suffix` child series, skip the undimensioned roll-up, discard series with no configured feed.
- **Page every list endpoint to exhaustion**, always sending `offset` and `limit` together, and validate the envelope rather than defaulting `items`.
- **Attribute existing alerts back to feeds** — Notifications on `(group, condition category, conf.name)`, monitors on exact-matched `rules[].includedTags` — counting only enabled alerts on a `health` or `volume` signal as coverage, skipping Cribl's `isDefault` monitors, recognising the `monitor-{id}` bridge as routing rather than an alert, and reporting anything unattributable as such.
- Discover Notification conditions and their JSON Schemas at runtime; generate the settings form from those schemas, **per direction**, and prune `conf` against the chosen condition.
- Classify conditions by what they watch, never by `type`; show `unclassified` alerts without counting them.
- Discover Insights metric names and the per-feed dimension label at runtime, for the sparkline only.
- **Discover the monitor host group by probing** `/m/{gid}/alert/monitors`, preferring the group that holds Cribl's shipped Stream monitors — never assuming it is the feed's own group, which it is not on the verification org.
- **Copy the monitor query verbatim** from a shipped `isDefault` `product: 'stream'` throughput monitor, and create no monitor for a direction that has no such template.
- **Check the host group's Insights engine before offering a monitor**, blocking creation on `red` and stating plainly when the check itself could not be read.
- Coverage table split into Sources and Destinations, each row carrying name, type, group, current health, a **separate error indicator** so a Green-with-error feed is visibly not fine, throughput sparkline, and **one coverage column** of clickable alert chips from both mechanisms, each chip qualified when it is not real coverage.
- Filters for group, direction, "no alerts yet," "currently unhealthy," and "has an error."
- State on the coverage summary that **Pack-scoped feeds are not covered**, so an incomplete table is not mistaken for a complete one.
- Multi-select rows plus a "select all uncovered" shortcut.
- Bulk-apply drawer: **mechanism per direction where there is a choice**, that mechanism's settings, notification targets or an explicit opt-out, and a disabled dry run that sets **both** senses (`disabled: true` on a Notification, `enabled: false` on a monitor).
- **Mandatory preview** listing every selected feed with its mechanism and **every object** that will be written, and a stated reason for anything not creatable — nothing created before explicit confirmation.
- Sequential creation with progress and honest per-item reporting including the created objects, **`partial` as a first-class outcome** when a monitor is written but its bridge is not, and retry of failures.
- **Alert configuration view** (Workflow 3): click a chip, see the stored object — schema-derived labels for a Notification, query/tags/per-threshold `enabled` for a monitor — with undeclared fields included, ownership claimed from evidence, and a link out to Cribl.
- Managed-alert registry **keyed per mechanism** and per-direction template defaults in KV, with reconciliation on load.
- Graceful degradation across **five** capabilities, with one notice per distinct problem and each mechanism blocking only itself.

**Nice-to-have (defer):**

- **Workflow 4 — per-alert tuning editor.** Highest-value deferred item; needs `PATCH` on `/notifications/*`, which is not granted, and would turn the monitor `PATCH` grant from a recovery into an editing affordance behind the same ownership check.
- **Workflow 5 — drift banner** surfacing newly added feeds with no alerts.
- **Workflow 6 — firing-history view** to spot noisy and suspiciously silent alerts. `/alert/history` 404s at the root; **re-probe it under `/m/{gid}/` first.** Monitors already deliver part of this for free on the Insights alerts page.
- **A per-object deep link** in the configuration view, once the UI route is confirmed (Verify First, item 5).
- **Pack-scoped feed coverage** — `/p/{pack}/system/inputs|outputs`, `includePacks` on `GET /notifications`. Implementation Rule 11 shows these feeds carry real traffic and real health, making this the most substantive coverage gap on this list.
- **Persistent-queue and backpressure alerting** from `backpressure-dest`, `persistent-queue-usage`, and `persistent-queue-usage-source` — all three confirmed present, and cheap because the form is generated from the schema. They are `unclassified` deliberately: neither answers "is data still moving", so promoting them means giving them their own column, not folding them into this one.
- **Alerting on `status.error` presence**, to close the Green-with-error blind spot. Needs a condition that can evaluate it server-side, and the catalogue offers none.
- Alerting on the per-type source metrics the discovery call already returns — `broken` / `activeBreakers` for TCP and Splunk, `numErrors` / `numDropped` for OTel.
- Distinguishing `Yellow` (degraded) from `Red` (critical) as separate severities in the display.
- Suggested thresholds computed from each feed's own observed baseline.
- Bulk disable and bulk delete of app-managed alerts.
- Edge fleet coverage in addition to Stream worker groups.
- Export the generated alert set as config for review or version control.
- **Percent-drop-versus-baseline, anomaly, forecast, outlier, and change detection.** Monitors exist now, and `rules[].conditions[].condition` is a flat `{type, threshold}` in every object captured — no window-over-window shape among them. So the gate is no longer "is there a monitor route" but **"capture a real monitor that does this before writing one"**; `openapi.json` is not evidence about this route, as it was wrong about `rules[]` too.
- **Alerting on a metric the shipped monitors do not measure.** Any such alert needs a composed query, which is out of scope. The step to take first is proving a hand-written expression against `POST /insights/metrics/query` and seeing it return series — not writing one into a monitor and hoping.

**Out of scope:**

- **Evaluating alerts in the app.** Cribl's engines do this. Non-negotiable.
- **A third mechanism, or an app-owned engine.** Two Cribl objects, both of them Cribl's. Anything that would evaluate a condition in this app — a poller, a rule engine, a timer deciding firing state — is out, because the app only runs while a tab is open.
- **Composing PromQL.** A monitor's query is copied from a shipped monitor or the monitor is not created. A hand-authored query that resolves to nothing is an alert that never fires.
- **Defining a custom health model.** Consume the platform's `health` verdict as-is and display it. Do not compute health from error counters, connection counts, or throughput — a second definition would disagree with the Cribl UI and erode trust in both.
- **Alerting on health as a separate intent.** Health is a display column. See Architectural Rule 2.
- **Sending notifications.** The app attaches existing targets; the platform delivers.
- **Creating or editing notification targets and policies.** Targets are read-only and policies are neither read nor written; the admin manages routing in the Cribl UI. This is why a monitor's bridge ships with empty `targets` and the UI says so. Creating the policy that *would* route monitor output is out of scope rather than deferred: a policy is shared routing configuration for the whole deployment, and an authoring tool must not quietly reshape where a deployment's alerts go. The app states that monitor delivery is governed by the deployment's Insights policies and leaves them to the admin.
- **Deleting anything.** No `DELETE` is granted on either collection. The monitor `PATCH` grant is the id-collision recovery inside create, not an edit path.
- **Authoring new Notification conditions.** The app uses what `GET /conditions` reports.
- **Modifying Sources, Destinations, pipelines, or routes.**
- **Changing Insights settings.** If Insights is off, explain and link out rather than enabling it.
- **Replacing Cribl's alerting UI.** No general-purpose alert browser, no silence management, no triage or acknowledgement.
- **Root-cause analysis.** The app answers "did this feed stop delivering?", not "why."
- **Edge fleets, Search, Lake, and Lakehouse coverage** for MVP.
- **Pack-scoped Sources and Destinations** for MVP — disclosed in the UI as a stated limitation, never silently omitted (Implementation Rule 11).
- **Non-admin personas.**

## Edge Cases & Error Handling

Each capability fails independently; **never blank the page.** Five capabilities are tracked — `alerting`, `monitors`, `insights`, `routingTargets`, `registry` — and **only `alerting` and `monitors` can block a write, each blocking only its own mechanism.** Everything else costs a column, a picker, or an ownership label. **Only both mechanisms being unavailable earns `danger`**; one of the two is a degraded app, not a broken one, and saying otherwise trains the admin to ignore the banner.

**One notice per distinct problem, not one per affected capability.** An earlier build produced four alerts saying the same sentence about the alert-monitor engine: two capability warnings, a per-group engine warning, and a line in the notice list. A stack of alerts nobody reads is worse than one that lands. So: collapse capabilities blocked with an **identical reason** into one notice naming what it costs; **do not report the downstream consequences of a blocked route at all**; and derive severity from whether alerting is *entirely* impossible rather than defaulting to `warning`. What must never be collapsed away is a capability the admin would otherwise assume is working.

**Scope a notice to what its evidence actually covers.** A denied `POST /notifications` is one deployment-wide problem, not one per group or per direction. Inventing a narrower claim than the evidence supports is how an earlier build reported a deployment-wide service failure as "the engine looks unavailable in `default`", once per group.

- **Notification write denied**: every Mechanism A item is blocked with the reason, **and the exact payload is still shown** so the admin can see what is gated and hand-build it if they must. It also blocks a monitor's *bridge*, which surfaces as a per-item `partial` rather than as a prediction up front — whether that write is permitted is only knowable by attempting it.
- **`GET /conditions` denied**: no condition id is known and none is ever guessed, so Mechanism A is blocked for both directions with that reason. It does **not** block a monitor, not even its bridge: the bridge uses the fixed `monitor-alerts` condition and consults no catalogue. Attribution of existing Notifications degrades, since a condition's `category` is what resolves their direction.
- **No matching condition for a direction**: Mechanism A is blocked for that direction with a reason stating the catalogue offers nothing that detects a feed of that direction no longer delivering data, and that condition ids are never guessed. The other direction, and monitors, are unaffected.
- **No group's `/m/{gid}/alert/monitors` answers**: the monitor mechanism is unavailable, naming every group probed and why. Notifications are unaffected.
- **A host answers but ships no throughput monitor to copy**: monitors are unavailable with the count of monitors found, stating that the app does not compose PromQL itself. If only one direction has a template, that is a notice, not a failure.
- **The host group's Insights engine reports `red`**: monitor creation is disabled rather than reported as working, because a monitor written there would not be evaluated. If the healthcheck could not be *read*, monitors stay creatable with an explicit "cannot confirm anything will evaluate them" notice — degraded honesty beats both a false success and a false block.
- **A monitor is created but its bridge fails**: reported as `partial` — "created, not routed." The monitor evaluates and appears on the Insights alerts page; it delivers nowhere until routing is attached. Never reported as a plain success.
- **`GET /notifications` denied**: coverage cannot be computed. Say so plainly rather than rendering every feed as uncovered — an inverted table is worse than a stated gap.
- **One worker group denied**: that group is skipped with a note; other groups render normally. One inaccessible group never fails the whole discovery pass.
- **Status endpoints denied**: only the `healthCounts` breakdown on row expand reads "unavailable." The base health column is unaffected because it arrives inline with discovery. Creation is still offered — the condition evaluates server-side whether or not the app can read the detail.
- **Notification targets denied**: alerts remain creatable with routing unset, stating that routing must be attached in Cribl separately. A single unrouted-alert warning, not one per item.
- **Insights denied, disabled, unhealthy, or absent**: **the sparkline column only.** Replace it with a short explanation and point at the setting; never render an empty chart with no explanation. **A Notification must never be gated on Insights**, and this is not the same capability as `monitors` — different paths, different failures. A dead sparkline says nothing about whether monitors work, and the two must not share a notice. This is the live case on the verification org, where `/system-insights/metrics` 404s at the root.
- **KV registry unreadable**: alerts are still creatable and coverage is still computed from the API; alerts simply cannot be labelled app-managed, and the view says ownership is **unknown** rather than denying authorship. Never let a failed registry read look like missing coverage, and never let it label the app's own alerts as somebody else's.
- **A feed's metric never matches**: suspect the `type:id` join (Implementation Rules 2 and 8–11) before concluding the feed has no data. Show "no data" distinctly from "not covered," so a join bug cannot masquerade as a quiet feed.
- **A discovered metric name returns no series**: say so and name the metric, rather than drawing an empty sparkline. Implementation Rule 13 shows this is a live hazard — two plausible-looking names silently matched nothing.
- **A feed appears in metrics but not in config**: discard it. It is internal plumbing, a roll-up, or a Pack feed (Implementation Rules 9–11) — never invent a table row from a metric series.
- **Partial bulk failure**: expected, and must not be hidden. Report per-item outcomes honestly, keep failed items selected, and let the admin retry without reconfiguring. **Do not swallow errors.** An alert created whose registry write failed reports both facts, as does a monitor created without its bridge.
- **A monitor id already exists**: `PATCH` recovers it and the outcome reads `updated`, not `created`. Any other rejection is surfaced as-is rather than retried — a blind `PATCH` after a denied `POST` could overwrite an object the app did not create.
- **A write is rejected mid-sequence**: continue the remaining items rather than aborting the batch, then report the full outcome.
- **Requests time out after 30 seconds** at the platform proxy. Use `AbortController` for anything the user can navigate away from.

**Write safety (from `AGENTS.md`, non-negotiable):**

- Creation happens only after the admin confirms the explicit preview. **Never create on render, mount, or a timer.**
- Updates and deletes apply only to app-managed alerts, behind a confirmation naming the object and stating when the action cannot be undone. The app deletes nothing, and its one `PATCH` is the id-collision recovery inside a create the admin already confirmed — not an edit of an object they did not ask about.
- Every volatile operation requires a deliberate button click and reports its outcome.

**Storage safety:** never `localStorage`, `sessionStorage`, `IndexedDB`, or cookies. The sandboxed iframe makes browser storage unreliable — it can be partitioned, cleared, or blocked, and is never shared across users, devices, or sessions.
