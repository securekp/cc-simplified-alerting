# Ally Monitoring App - App Brief

## App ID

`ally-monitoring` — display name **Ally Monitoring App**. Matches the existing scaffold's `package.json`; no rename needed.

## Problem & Vision

Cribl already has every ingredient for per-Source and per-Destination alerting: health status on every input and output, Insights throughput telemetry, a Notification engine that fires on health conditions, and an alert-monitor engine that fires on metrics. What's missing is a fast path from "here are my enabled Sources and Destinations" to "each one is watched."

Today an admin has to hand-author each alert in the Cribl UI, know which of the two engines fits which signal, look up the right condition or metric and label filter per feed, and repeat all of it every time a feed is added. It doesn't happen, so deployments run with no per-feed alerting at all.

This app auto-discovers what is actually enabled, shows what is already covered, and creates alerts from templates in a few clicks. It covers two complementary failure modes:

1. **Connectivity — defined as the health of the Source or Destination.** Cribl's own aggregated `health` verdict (`Green` / `Yellow` / `Red` / `Unknown`), not a proxy derived from error counters or throughput.
2. **Throughput** — volume dropping off relative to baseline. Catches loss that health will not: a Destination can be perfectly healthy while the Source feeding it has gone quiet.

Neither substitutes for the other, which is why the app creates both per feed.

**The vision in one line:** install to a meaningful set of alerts in one sitting, without first learning which mechanism to use, what the condition IDs are, or what the Insights metric names and label filters look like.

## Target Users

**Cribl platform admins, exclusively.** They own the Stream deployment, configure the feeds, and are accountable for whether data still flows end to end. They have admin API access and can see all worker groups.

Ops / on-call engineers and data owners are *consumers* of the alerts, not users of the app — they receive them through whatever notification target the admin attaches and never need to open it. Baseline today is zero coverage and reactive discovery (someone downstream notices missing data and complains), so there is no import or migration path to build.

## Two Architectural Rules (read before writing any code)

### Rule 1: This is an authoring tool, never an evaluator

The app writes alert configuration to Cribl and never evaluates anything itself. The app runs in a sandboxed iframe with no background runtime — an app-owned alert engine would only evaluate while a browser tab was open, which is useless for alerting. Delegating to Cribl's engines means alerts keep firing when the app is closed or uninstalled, appear in Cribl's native UI and history, and reuse existing targets, policies, and silences.

**Non-negotiable:** no polling loops that check thresholds, no in-app rule engine, no timers that decide whether something is firing.

### Rule 2: Two native mechanisms, matched to the signal — do not collapse them into one

| Intent | Mechanism | API |
|---|---|---|
| Connectivity (health) | Cribl Notification on a discovered health condition | `POST /notifications` |
| Connectivity (fallback) | Alert monitor over `health.inputs` / `health.outputs`, rule `health != 0` | `POST /alert/monitors` |
| Throughput — volume drop | Alert monitor over Insights metrics | `POST /alert/monitors` |
| Throughput — total stop (Sources) | Cribl Notification on the native `no-data` condition | `POST /notifications` |

Note the last row: a throughput *intent* is not always a monitor. "No data at all" on a Source is best served by a Notification condition, so do not build the throughput path as monitors-only.

Health is not a metric and should not be forced into a metric query where a purpose-built condition exists. Notification conditions consume the platform's own health verdict (so the app agrees with the Cribl UI), give sustained-state detection via `timeWindow` without flapping, give recovery notices via `notifyOnResolution`, and are per-feed by construction via `conf.name`.

Shape of a connectivity Notification:

```json
{
  "id": "unhealthy-splunk-dest",
  "condition": "unhealthy-dest",
  "targets": ["system_notifications"],
  "conf": { "name": "out_splunk", "timeWindow": "60s", "notifyOnResolution": true }
}
```

**Discover conditions, never hardcode them.** Call `GET /conditions?category=sources` and `?category=destinations`. Each condition returns a JSON Schema for its `conf` fields — titles, descriptions, patterns, duration minimums — so **generate the configuration form from that schema**. A renamed or new condition in a future Cribl version then appears automatically instead of breaking the app.

**Status of `/conditions`:** the *contract* is fully documented in `openapi.json` — `GET /conditions` takes `category`, `showHidden`, `offset`, `limit` and returns a `PaginatedConditionResponse`. What is unverified is the *content*: which health conditions a deployment offers, notably whether a Source-side health condition exists alongside `unhealthy-dest`. Not a blocker — the metric route is confirmed live for *both* directions, so Notifications are the preferred path where a matching condition exists and the metric-monitor path is a verified universal fallback. Never fabricate a condition ID. **Hidden conditions are excluded by default** — set `showHidden` deliberately rather than by omission.

Throughput detection methods the admin picks from:

* **Absolute floor threshold** — fire below a fixed bytes/events value, including zero. Directly expressible as a `MonitorQuery` plus a rule, so it is the one method that can be built with confidence. **This is the shipped default.**
* **No data at all** — for Sources, the native `no-data` ("No Data Received") Notification condition, offered alongside the metric methods since it needs no threshold.
* **Percent drop versus baseline** — current window versus prior window or same window last week. Conceptually the best default, because it scales across feeds of wildly different sizes without per-feed tuning. **But it has no verified mechanism on `/alert/monitors`, so the UI must not offer it until one is proven** (see Verify First). It was previously written up as "the default"; that was wrong.
* **Anomaly / forecast / outlier / change monitor types** — deferred, and **on a different endpoint**. `MonitorType` (`threshold | change | anomaly | forecast | logs | outlier`) and `detectionConfig` (`ChangeConfig`, `AnomalyConfig`, `ForecastConfig`, `OutlierConfig`) belong to `AetosMonitorConf`, used in `openapi.json` only by `/products/lakehouse_engine_metrics/monitors`. The `MonitorConf` body that `/alert/monitors` accepts has **no type or detection-config field at all** — which is precisely why percent-drop cannot simply be declared and has to be hand-rolled in the query string.

**In the UI:** the admin picks an *intent* ("alert me when this Destination is unhealthy"), and the app picks the mechanism. Never hide which was used — label each created alert and link out to it in the native Cribl UI.

## Implementation Rules Proven Against a Live Deployment

Verified empirically against a real Cribl Cloud org, not inferred from the spec. Each of these silently produces a wrong-looking table if ignored, so treat them as requirements.

1. **Health arrives inline with discovery.** `GET /m/:gid/system/inputs` and `/system/outputs` already return `status.health` as a string, plus a per-type `status.metrics` object and (Destinations) `status.error`. **One call per group per direction fills the whole coverage table on first paint.** `/system/status/*` is a lazy progressive enhancement, fetched only when a row expands for `healthCounts`.
2. **`0` = Green, `2` = Red in the metric store** — cross-checked on two independent feeds whose `status.health` read `"Red"`. `1` (presumably Yellow) and the Unknown value were not observed. **Express the connectivity rule as `health != 0`, never `health == 2`** — correct regardless of how the unobserved states are numbered, and it naturally catches degraded and unknown as well as critical.
3. **Join on `type` + `id`, and match exactly.** Metric dimension values are fully qualified `type:id` (`syslog:in_syslog:udp`, `splunk_hec:in_splunk_hec`, `cribl_lake:palo_traffic`) while config objects key on the bare `id`. **IDs can themselves contain colons and protocol suffixes** — `syslog:in_syslog:udp` is type `syslog`, id `in_syslog`, plus a `:udp` suffix. Construct `` `${type}:${id}` `` from the config object and compare for **exact equality**; never split the dimension value back apart, and never prefix-match (see rule 9). **This is the single most likely cause of silently mismatched coverage** — a feed that looks uncovered because its metric never matched.
4. **Green does not mean fine.** Three Destinations were observed `"Green"` while carrying `status.error.message = "There is an issue with the underlying destinations."` Surface `status.error` as its own always-visible indicator so a Green-with-error feed is visibly not fine. Do **not** redefine health to compensate — that would put the app's verdict at odds with the Cribl UI's, the exact thing this design avoids.
5. **Check the monitor engine before creating monitors.** The monitor service (**`aetos`**) was observed down independently: "The service failed to boot due to: No workers registered", group at `workerCount: 0`. Query `GET /health` and the system-messages feed, and warn the admin rather than reporting success for a monitor that can never fire.
6. **Filter groups on `type === 'stream'` in app code.** Asking for Stream groups returned `outpost`-type groups too. Do not trust the request parameter.
7. **Filter feeds on `disabled !== true`.** Disabled feeds still report health (observed `disabled: true` with `"Green"`). Health is never the enabled test.

Rules 8–13 come from a second live pass on 2026-09-01 that queried the metric store directly. Rules 1–7 were re-verified unchanged in the same pass; rule 8 **corrects** metric names this brief previously stated.

8. **The throughput metric names are `total.in_bytes` / `total.out_bytes` / `total.in_events` / `total.out_events`.** Dot-separated, no `cribl.` prefix, no `_total` suffix. Queried live: `sum("total.in_bytes")` returned `217902914` over 1h, while **`sum("cribl.in_bytes_total")` and `sum("cribl.events_in_total")` — the names this brief previously specified — matched no series at all.** The underscore form `total_in_events`, which is what the `POST /alert/monitors` example in `openapi.json` uses, **also matched nothing**. So neither the old brief names nor the spec example's name is portable. **Discover names at runtime from `GET /system-insights/metrics`; the names here are for sanity-checking discovery output, not for hardcoding.** When a discovered name yields no series, say so visibly instead of drawing an empty sparkline.
9. **One logical feed emits several metric series — summing them double-counts.** Observed: `subscription:palo_traffic_filtering` *and* `subscription:palo_traffic_filtering:test`, both `bytes = 3169258`; `subscription:zscaler_web_project` *and* `...:zscaler`, both `84603299`; plus `syslog:in_syslog`, `:udp`, `:tcp`. The parent and its `:suffix` children carry the **same** value, not complementary halves. Match the parent exactly; a `startsWith` join would double or triple a feed's apparent throughput and silently corrupt every threshold derived from it.
10. **There is a roll-up series with no `input` / `output` dimension**, equal to the ungrouped total. Exclude it, or the table gains an unnamed row and the coverage count is off by one.
11. **The metric store contains far more feeds than the config calls, including internal plumbing.** `health.inputs` returned 47 series — among them `ServiceTcp:search`, `ServiceTcp:notifications`, `cribl:CriblLogs`, `http:http`, `router:engine_router`, `local_search_storage:engine_kptest` — against a config list of user feeds; `health.outputs` returned 32 series against 17 configured destinations. **The config call is the spine and metrics are joined onto it, never the reverse.** Discard unmatched series silently; a configured feed with no series shows "no data," which is distinct from "not covered."
12. **Pack-scoped feeds have health and traffic but no row in the group config call.** The metric store returns `type:packName.feedId` values — `datagen:cribl-palo-alto-networks.palo_traffic` (33 MB/h), `open_telemetry:observeai.observeai-claudeDesktopOTLP` (180 KB/h), `splunk_hec:cribl-crowdstrike-rest-io.out_splunk` — none of which appear in `GET /m/default/system/outputs` or `/system/inputs`. The same feed can even appear both pack-qualified and bare across different metrics. **MVP excludes Pack feeds and the UI must say so on the coverage summary**, so a partial table is not read as a complete one. `/p/{pack}/system/inputs|outputs` and `includePacks` on `GET /notifications` are how a later version closes this.
13. **`status.health` can be absent entirely, not merely `Unknown`.** The synthetic `default` destination returned `status: {}` — no `health`, no `timestamp`, no `metrics`. Treat missing as `Unknown` and exclude it from the healthy tally; treating it as falsy-therefore-Green reports a feed healthy on no evidence. Also: `status.metrics` was `{}` on **every** destination in this snapshot while Sources returned populated per-type metrics — so per-type `status.metrics` is a Source-side signal and must not be relied on for Destinations.

## Verify First, In Priority Order

Everything in the Implementation Rules above is settled. These are the open questions, ordered by how much MVP they block. Do item 1 before writing the throughput path.

1. **How a threshold is expressed in `MonitorConf.rules[]`.** `rules` is *required*, so no monitor can be created without it, and the mandatory preview promises the admin "the exact threshold." Yet the spec gives no usable schema: `Rule.conditions[]` holds `LabelCondition`, whose `condition` field `$ref`s `Condition`, which `$ref`s `Function` — the *pipeline function* schema (`__conf`, `__filename`, `uischema`, `initTime`, …). That is an OpenAPI generator name collision, not a real contract, and the spec's own create example ships `rules: []`, so it demonstrates nothing. **Resolve by inspecting a real monitor from a working org (`GET /alert/monitors`).** Both throughput alerting and the metric-based connectivity fallback depend on it.
2. **Whether percent-drop-versus-baseline is expressible at all** on `/alert/monitors`, given `MonitorConf` has no `type` / `detectionConfig`. Until proven, absolute floor is the default and percent-drop is not offered in the UI.
3. **Where notification policy IDs come from**, for monitor routing. No listing endpoint found.
4. **Which health conditions the deployment offers** — the `GET /conditions` contract is documented, its content is not; specifically whether a Source-side health condition exists alongside `unhealthy-dest`. Runtime discovery already handles either answer, so this blocks nothing.
5. **Whether discovered Insights metric names are queryable through `POST /insights/metrics/query`** under the same names the catalogue reports, given that neither `cribl.in_bytes_total` nor the spec example's `total_in_events` matched any series (Implementation Rule 8).

`GET /conditions` was previously written up as the headline unknown. It is not — the spec documents it fully. Item 1 is the real one.

## Key Workflows

### Workflow 1: Review Alert Coverage (landing view) — MVP

- **User sees**: One dense table of every enabled Source and Destination across accessible Stream worker groups. Columns: name, type, group, direction, current health, a separate error indicator, recent throughput sparkline, connectivity-alert coverage, throughput-alert coverage. A header coverage summary ("34 of 51 feeds covered, 2 unhealthy"). An unhealthy feed with no connectivity alert is styled as the most important row in the app.
- **User does**: Sorts, searches, and filters to find the gaps — by group, by direction, "no alerts yet," "currently unhealthy," "has an error." Expands a health cell to see the per-Worker-Process breakdown.
- **Result**: Nothing is written. This is a read-only audit that answers "what is flowing, is it healthy, and what is watched?"
- **Permissions**: Renders whatever the API returns for the signed-in user. No app-level filtering — Cribl RBAC and worker-group ACLs are the single source of truth. An admin with access to two of five groups sees two groups' worth of feeds, presented as normal rather than as an error.

Load sequence: list groups (`GET /master/groups`, filtered to `type === 'stream'`) → per group fetch inputs and outputs (health inline, filter `disabled !== true`) → discover conditions and the Insights metric catalog → fetch existing Notifications and monitors, **paging each to exhaustion**, and match them back to feeds via the reverse-matching algorithm → reconcile the KV registry → render. Sparklines (batched one query per group per direction) and `healthCounts` load after first paint.

### Workflow 2: Bulk-Create Alerts From a Template — MVP, the primary value workflow

- **User sees**: A sticky action bar once rows are selected ("N selected — Create alerts"), opening a side drawer: alert types → connectivity settings → throughput method and parameters → notification routing → **preview** → confirm.
- **User does**: Multi-selects rows (with "select all uncovered" as a shortcut); picks connectivity, throughput, or both; sets the connectivity sustained window and whether to notify on resolution (**fields generated from the discovered condition's JSON Schema, including its duration minimum, so an invalid value cannot be offered**); picks the throughput detection method, parameters, evaluation window, and schedule; attaches an existing notification target or policy, or opts to create the alerts disabled for now.
- **Result**: After an explicit confirmation, sequential `POST /notifications` for connectivity and `POST /alert/monitors` for throughput, with progress feedback. Per-item success and failure reported honestly. Coverage table refreshes and newly covered rows flip to covered. Each created alert is registered in KV and links out to the native Cribl UI.
- **Permissions**: Requires write access to the relevant engine. Denial of one engine does not block the other (see Edge Cases).

**The preview step is mandatory and cannot be skipped.** It lists one row per alert that will be created, stating the feed it watches, the mechanism (Notification or Monitor), the exact condition or metric query, the threshold, and the window. Nothing is created before the admin confirms. Partial failure is expected and must not be hidden — failed items stay selected so they can be retried without redoing the configuration.

Before offering throughput creation, check the monitor engine is alive and warn if not.

### Workflow 3: Tune an Individual Alert — deferred (highest-value deferred item)

- **User sees**: An editor for one alert. Connectivity editors generated from the condition schema; throughput editors exposing metric, threshold, evaluation window, `schedule_interval_seconds`, `firing_after` / `ok_after`, severity rules, and routing. Alongside it, recent Insights history versus the proposed threshold (throughput) or recent health transitions (connectivity), so the admin can see whether it would have fired against real traffic.
- **User does**: Clicks a row's alert, adjusts settings, saves. Or disables rather than deletes.
- **Result**: A confirmed overwrite of the underlying object, naming it explicitly. Outcome reported.
- **Permissions**: Applies only to alerts this app manages, so the app never silently overwrites something a human hand-built. Delete requires an explicit confirmation naming the object and stating the action cannot be undone.

### Workflow 4: Re-Scan for Coverage Drift — deferred

- **User sees**: A banner on return — "N new Sources and M new Destinations have no alerts."
- **User does**: Selects the new items and runs Workflow 2 against them, reusing the last-used template settings from KV.
- **Result**: Coverage keeps pace with a deployment that keeps growing.
- **Permissions**: Same as Workflow 2.

### Workflow 5: Verify Alerts Are Working — deferred

- **User sees**: An alert-activity view — which alerts have fired, how often, and which have never fired.
- **User does**: Spots noisy alerts and suspiciously silent ones, then jumps to Workflow 3 to retune.
- **Result**: Read-only. Closes the loop so the admin trusts what they built.
- **Permissions**: Requires read access to `/alert/history`.

## Data & Actions

**The app will fetch from Cribl:**

- **Stream worker groups** — `GET /master/groups`. Scopes discovery and labels rows (Workflow 1). Filter to `type === 'stream'` in app code.
- **Enabled Sources and Destinations, with health inline** — `GET /m/:gid/system/inputs`, `GET /m/:gid/system/outputs`. Name, ID, `type`, `disabled`, `status.health`, per-type `status.metrics`, and (Destinations) `status.error`. The backbone of Workflow 1; filter `disabled !== true`.
- **Per-Worker-Process health detail** — `GET /m/:gid/system/status/inputs`, `/system/status/outputs`. Adds `healthCounts` per state and `pq` queue status. Fetched lazily on health-cell expand only (Workflow 1).
- **Health as a metric** — `health.inputs` (dim `input`), `health.outputs` (dim `output`), queried with **`POST /system/metrics/query`**. `GET /system/metrics` is a different, GET-only endpoint and is *not* how series are fetched; `POST /system/metrics/enum` enumerates dimension values. Verified live with `max()` as the aggregation. Powers the connectivity fallback rule `health != 0` (Workflow 2) and health-transition history (Workflow 3).
- **Notification conditions and their schemas** — `GET /conditions?category=sources`, `?category=destinations`, `GET /conditions/{id}`. Drives schema-generated connectivity forms (Workflows 1 and 2). Never hardcode IDs or field names. Paginated, and hidden conditions are excluded unless `showHidden` is set.
- **Throughput history from Insights** — `POST /insights/metrics/query`. Metric expressions over names **discovered at runtime**; on the verification org those were `total.in_bytes`, `total.in_events`, `total.out_bytes`, `total.out_events` (Implementation Rule 8 — the `cribl.*` names previously listed here matched no series). Sent with `dimensionFilters` including `{name: "namespace", operator: "eq", value: "data_insights"}` plus the group, and `dimensionSplits` on the per-feed dimension. Drives row sparklines (Workflow 1) and the threshold-versus-history preview (Workflow 3).
  - **Batch, do not fan out:** one query per group per direction with `dimensionSplits`, not one per row. Dozens of feeds against a 30-second proxy timeout makes per-row querying a guaranteed timeout.
  - Apply Implementation Rules 9–11 when reading results: exact-match the dimension value, skip `:suffix` children, skip the undimensioned roll-up, discard unmatched series.
- **Insights metric catalog** — `GET /system-insights/metrics` for names, `GET /system-insights/metrics/{id}` for label names and values. **The per-feed dimension label is discovered here at runtime, not hardcoded** (Workflows 1 and 2).
- **Insights health and settings** — `GET /system-insights/healthcheck`, `GET /system/settings/insights`. Lets the app explain a blank chart instead of rendering one.
- **Service health** — `GET /health` plus **`GET /system/messages`** (the system-messages feed; paginated, returns `count` / `offset` / `limit` / `totalCount`). Detects a dead monitor engine before Workflow 2 creates monitors. Detection: `severity: "error"` and an `id` beginning `SERVICE_DOWN_` — re-verified live as `SERVICE_DOWN_aetos`, "The service failed to boot due to: No workers registered," with the `default` group still at `workerCount: 0`. Corroborate with that `workerCount` — but only when it is present. `defaultHybrid` omits the field entirely, so `workerCount` is `number | null` and `null` is never treated as zero, never quoted as evidence, and never blocks creation.
- **Existing alerts** — `GET /notifications` (accepts a **`groupId`** filter and an `includePacks` flag), `GET /alert/monitors`. Matched back to the feed each targets to compute the coverage columns (Workflow 1) and reconcile the registry. **See "Matching existing alerts back to feeds" below — this is not a trivial lookup.**
- **Notification targets** — `GET /notification-targets`, to populate the routing picker for **connectivity Notifications only** (their `targets` field takes notification *target* IDs). Monitors take a different kind of ID — see the routing note under write payloads. `GET /notifications` is the alert-object list and **must not** be used to populate a policy picker.
- **Alert firing history** — `GET /alert/history`, `GET /alert/history/stats` (Workflow 5, deferred).

**Page every list endpoint to exhaustion.** `GET /notifications`, `GET /alert/monitors`, `GET /conditions`, and `GET /system/messages` all take `offset` / `limit` and return paginated envelopes. Reading only the first page makes existing alerts invisible, which renders covered feeds as **uncovered** — the same silent-miscoverage failure the `type:id` join rule guards against, reached by a different route.

**`limit` and `offset` are all-or-nothing.** Verified live: `?limit=200` without `offset` is rejected by every list endpoint with `{"status":"error","message":"missing 'offset' parameter, 'offset' is required when 'limit' is provided"}`. The error body has **no `items` key**, so `body.items ?? []` would read it as "nothing configured" and invert the whole coverage table. Both paginators build `{ ...query, offset, limit }` in a single object so the pair cannot be split, and `assertPaginated` rejects any envelope without `items` instead of defaulting it.

**Endpoint availability is discovered, not assumed.** On the verification org several endpoints `openapi.json` documents as `GET` return Express 404s — `/alert/monitors`, `/alert/history`, `/system-insights/metrics`, `/system-insights/healthcheck` — while `/conditions`, `/notifications`, `/notification-targets` and `/system/settings/insights` answer. The only live monitors endpoint is `/products/lakehouse_engine_metrics/monitors`, empty and on a different schema. Treat a documented path as a hypothesis: probe it, offer the capability only if it answers, and name the missing endpoint in the degradation reason.

**Matching existing alerts back to feeds.** The forward join is specified in Implementation Rule 3. The reverse direction is what the coverage columns actually depend on, and it must work for alerts the app did not create:

- **Notifications:** `conf.name` holds the **bare feed ID** — no `type`, no direction. A Source and a Destination sharing an ID are indistinguishable from `conf.name` alone. Resolve direction from the **condition's `category`** (`sources` vs `destinations`) in the discovered condition catalogue, and scope by the Notification's `group`. Match on `(group, direction, id)`.
- **Monitors:** there is no feed field. Recover ownership by reading the `MonitorQuery`'s `labelFilters` for the `input` / `output` label and comparing to the constructed `` `${type}:${id}` ``. If a monitor's `query` is a PromQL **string** rather than an object, **do not parse it** — report it as present-but-unattributable and do not count it toward coverage.
- **Never guess.** An alert that cannot be attributed to exactly one feed is listed as unattributed, not silently dropped and not counted twice.

**The app will create/modify/delete in Cribl:**

- **Creates Notifications** — `POST /notifications`, one per feed, using a discovered condition with `conf.name` set to the feed ID, `conf.timeWindow` for the sustained window, `conf.notifyOnResolution` for recovery notices (Workflow 2). This covers **connectivity** where a health condition exists (`unhealthy-dest`, Destinations) **and throughput** where a volume condition exists (`low-volume`, Sources).
- **Creates alert monitors** — `POST /alert/monitors`, one per feed, for whichever intent and direction the condition catalogue does not cover. Live, that is Source connectivity and Destination throughput (Workflow 2).

### Write payloads — build exactly these shapes

**Connectivity Notification** (`POST /notifications`). Required by the schema: only `id` and `condition`. The app sets five fields:

```json
{
  "id": "ally-conn-out_splunk",
  "condition": "unhealthy-dest",
  "group": "default",
  "targets": ["system_notifications"],
  "disabled": false,
  "conf": { "name": "out_splunk", "timeWindow": "60s", "notifyOnResolution": true }
}
```

`conf` field names and constraints come from the discovered condition's JSON Schema, **not** from this example — the `timeWindow` / `notifyOnResolution` names above are illustrative of the shape only.

**Throughput Notification** (`POST /notifications`) — the preferred throughput route, used wherever the catalogue offers a volume condition. Same engine and same shape as the connectivity Notification, differing only in the condition and the id prefix:

```json
{
  "id": "ally-thru-in_splunk_hec",
  "condition": "low-volume",
  "group": "default",
  "targets": ["system_notifications"],
  "disabled": false,
  "conf": { "name": "in_splunk_hec", "dataVolume": 1024, "timeWindow": "60s", "notifyOnResolution": true }
}
```

Again the `conf` field names come from that condition's own JSON Schema, pruned against it — `low-volume` declares `dataVolume`, which `unhealthy-dest` does not, so the two intents must not share one `conf` bag. **`conf.name` is always set from the feed and never from the template**: Cribl's `uischema` marks it `ui:disabled: true` with `default: "${IO_ID}"`. This route needs neither a metric name nor a live monitor engine, so it must not be gated on Insights or on `aetos`.

**Throughput monitor, absolute floor** (`POST /alert/monitors`, body is a `MonitorConf`) — the fallback, for a direction with no volume condition. Required: `id`, `name`, `product`, `query`, `rules`, `params`, `enabled`, `firing_after`, `ok_after`, `schedule_interval_seconds` — note `product` and `params` are required and easy to miss.

```json
{
  "id": "ally-thru-in_splunk_hec",
  "name": "Ally — throughput floor: in_splunk_hec",
  "product": "stream",
  "enabled": true,
  "query": {
    "metricName": "total.in_bytes",
    "operation": { "operation": "sum" },
    "timeRange": "5m",
    "labelFilters": [
      { "label": "input", "operator": "=", "value": "splunk_hec:in_splunk_hec" },
      { "label": "__worker_group", "operator": "=", "value": "default" }
    ]
  },
  "rules": [],
  "params": {},
  "firing_after": 300,
  "ok_after": 300,
  "schedule_interval_seconds": 60
}
```

**Connectivity fallback monitor** — identical shape with `metricName: "health.inputs"` (or `health.outputs`), `operation: "max"`, and the rule expressing `health != 0`.

`query` is `oneOf` a PromQL **string** (what the spec's own example uses: `sum(rate(total_in_events{namespace="data_insights"}[1m]))` — note that metric name matched no live series) or a **`MonitorQuery` object**. **Use the object form.** It is the better-specified route, it maps directly onto "aggregate one metric, filtered to one feed," and it keeps the monitor machine-readable so the reverse-matching algorithm above can attribute it later. Hand-assembled PromQL is unvalidatable by the app and unattributable on read-back.

`rules: []` above is a **placeholder, not a working monitor** — see Verify First, item 1. `rules` is required and is where the threshold and severity actually live.

**The two engines spell their comparison operators differently, and the wrong one silently matches nothing.** A monitor's `labelFilters` use `MonitorQueryLabelFilterOperator`, whose enum in `openapi.json` is `=` / `!=`. The Insights query's `dimensionFilters` use `eq` / `exists`. They are not interchangeable: `operator: "eq"` in a monitor label filter is not a valid enum member.

**Group scoping differs between the two mechanisms, and getting it wrong is a correctness bug.** In a multi-group deployment — the stated scope:

- **Notifications are group-scoped by a field:** set `group` on create, and read back with the `groupId` query parameter.
- **Monitors are not.** `MonitorConf` has no group field, only the required `product: "stream"`. **The group must be carried in the query's `labelFilters`** (the `__worker_group` filter above). Omit it and a monitor created for `splunk_hec:in_splunk_hec` in one group also matches a same-named feed in another — firing for the wrong deployment and attributing coverage to both rows.

**Routing is two different models — the drawer's routing step must be per-mechanism.**

- **Notifications** take `targets`: notification *target* IDs from `GET /notification-targets`. Verified present.
- **Monitors** take `notification_policies`: notification *policy* IDs. **No endpoint in `openapi.json` lists notification policies** — the only `*polic*` paths are `/system/policies`, `/apps/{id}/policies`, `/search/trust-policies`, all unrelated. Until a listing endpoint is identified, offer monitor routing as free-text policy IDs with a stated caveat, or leave it unset and say routing must be attached in the Cribl UI. **Do not present one merged "target or policy" picker over two incompatible ID spaces.**

**Creating alerts disabled** is supported by both engines with **inverted senses** — an easy bug: Notifications use `disabled: true`, monitors use `enabled: false` (and `enabled` is required).
- **Modifies** only the Notifications and monitors it manages, when the admin tunes a window, threshold, schedule, routing, or enabled state (Workflow 3). A volatile overwrite: always confirmed, naming the object, never triggered on render or a timer.
- **Deletes** only on explicit admin action, behind a confirmation naming the object and stating the action cannot be undone (Workflow 3).
- **Never modifies** Sources, Destinations, pipelines, routes, notification targets, notification policies, or Insights settings. The app reads platform configuration and writes only alerting configuration. Insights settings are read to *explain* a problem, never written to fix one.

**The app will remember (general state):**

All persistence uses the **app-scoped KV store** (`CRIBL_API_URL + '/kvstore/...'`).

- **Managed-alert registry** — `ally-monitoring/managed/{kind}/{id}` where `kind` is `notification` or `monitor`. One record per alert the app created: ID and kind, worker group, feed ID, direction, alert type, and template settings used. Because the app writes to two engines, an explicit registry is what lets a single coverage column answer "is this feed watched?" without inferring ownership from names a human could rename or that could collide with hand-built alerts. It also distinguishes app-managed from hand-built, so the app never silently overwrites something it didn't create.
  - **This is a cache, not the truth.** On load, reconcile against `GET /notifications` and `GET /alert/monitors`: drop entries whose object no longer exists, and count unregistered alerts toward coverage as "unmanaged." **A stale entry must never make an uncovered feed look covered.**
- **Last-used template settings** — `ally-monitoring/template-defaults`. Connectivity `timeWindow` and resolution preference; throughput method and parameters, evaluation window, `schedule_interval_seconds`, `firing_after` / `ok_after`; selected notification target or policy. Stored at app scope so the whole admin team applies consistent windows and thresholds, and so the recurring "new feeds appeared, cover them the same way" pass is near-one-click.

**User-specific settings (stored per user):**

**None** — deliberately. View preferences (selected group, filters, sort order) live in component state and the URL only, never in KV. Every admin sees the same deployment-wide coverage picture on open, which is the right default for a shared operational tool: a remembered filter is exactly how someone misses an uncovered source.

**Secure secrets:**

**None.** The app makes no external calls and holds no third-party credentials. Cribl API authentication is injected by the platform's fetch proxy — the app never sees a token. Alert delivery credentials belong to the notification targets the app references by ID.

## UI Structure

### Overall Layout

**Table-first with a bulk-apply drawer.** One dense coverage table is the home screen and the entire product surface for MVP. Selecting rows opens a side drawer to configure, preview, and confirm — **no page navigation between finding the gaps and fixing them.**

Rationale: the admin's job is a sweep across dozens of feeds. A wizard optimises for one careful item at a time and would make the real task tedious; a dashboard optimises for looking rather than doing. The table keeps the gap list and the fix in one view, and the drawer keeps context visible while configuring.

### Key Screens/Pages

1. **Coverage table (home)** — Header: worker-group selector, direction filter, "uncovered only" / "unhealthy only" / "has an error" filters, free-text search, coverage summary. Table: one row per enabled feed with a leading selection checkbox, a health cell that expands to lazily load per-Worker-Process `healthCounts`, an always-visible `status.error` indicator, a throughput sparkline, two coverage columns, and a per-row action to inspect its alerts. Sticky action bar when rows are selected.
2. **Bulk-apply drawer** — Steps: alert types → connectivity settings (rendered from the condition schema) → throughput method and parameters → notification routing → **preview list** → confirm. Preview is not skippable. Inline per-item outcomes after apply, with failures retryable and still selected.
3. **Per-alert tuning editor** *(deferred, Workflow 3)* — schema-generated form plus threshold-versus-history or health-transition chart.
4. **Alert activity view** *(deferred, Workflow 5)* — firing counts, never-fired list.

Routing uses React Router with `basename={window.CRIBL_BASE_PATH}`. Filter and group selections live in the URL so a view can be shared or reloaded.

### Look / Feel

**Capra design system** (`@capra/core`, `@capra/icons`, `@capra/theme`), already in the scaffold — see https://capra.cribl.io/llms.txt. The app should look like a native part of the Cribl UI, not a bolted-on tool.

- Use Capra design tokens in CSS via the custom `token()` function — **never a raw CSS variable**.
- **Do not apply CSS classes to Capra components**; handle spacing with wrapper elements outside them.
- **Do not write selectors that depend on Capra internals, class names, or DOM structure.**
- Dense, scannable table styling — this is an operational audit view, not a marketing page.
- Health uses Capra's semantic status tokens so `Green` / `Yellow` / `Red` / `Unknown` read correctly in both themes without custom colour handling and match how health is coloured elsewhere in Cribl.
- Coverage state carries clear visual weight: **an unhealthy feed with no connectivity alert should be the first thing the eye lands on**, and uncovered feeds should stand out from covered ones.

## Permissions & Access

- **Who can use this app?**: Cribl platform admins. Whoever an admin shares the app with, subject to the paths declared in `config/policies.yml`.
- **No app-level filtering**: the app renders whatever the Cribl API returns for the signed-in user. Cribl's RBAC and worker-group ACLs are the single source of truth. The app adds no parallel authorization logic — a second access model would drift from the platform's and give a false impression of what a user can see.
- **Permission-aware behavior**: every capability fails independently and names both the missing permission and what the user can still do. Never a generic error, never an empty screen. See Edge Cases.

Declare every Cribl API path the app calls in `config/policies.yml`, **including the `/m/:gid/...` variants**. Note that `openapi.json` contains **no `/m/{gid}/...` paths at all** — the group prefix is a leader-side convention layered over the flat paths, so it must be declared explicitly rather than inferred from the spec. The full set: `/master/groups`, `/m/:gid/system/inputs`, `/m/:gid/system/outputs`, `/m/:gid/system/status/inputs`, `/m/:gid/system/status/outputs`, `/system/metrics/query`, `/insights/metrics/query`, `/system-insights/metrics`, `/system-insights/metrics/{id}`, `/system-insights/healthcheck`, `/system/settings/insights`, `/conditions`, `/conditions/{id}`, `/notifications`, `/alert/monitors`, `/notification-targets`, `/health`, `/system/messages`, and the KV store paths.

## External Integrations (if any)

**None.** Every call goes through the Cribl API. `config/proxies.yml` stays empty, there is nothing external for an admin to approve at install time, and the app holds no third-party credentials.

Alert delivery is the platform's job: the app attaches an existing notification target or policy to each alert it creates and Cribl handles Slack, email, or PagerDuty delivery. **The app never sends a notification itself.**

## MVP Scope

**Must-have:**

- Discover Stream worker groups, filtering to `type === 'stream'` in app code.
- Discover Sources and Destinations per group with health inline, filtering out `disabled === true`, treating a **missing** `status.health` as `Unknown` rather than healthy.
- Correctly join config objects to metric dimension values: construct `` `${type}:${id}` `` and match **exactly** — no prefix matching, no splitting the dimension value apart, skip `:suffix` child series, skip the undimensioned roll-up, discard series with no configured feed.
- **Page every list endpoint to exhaustion** (`/notifications`, `/alert/monitors`, `/conditions`, `/system/messages`).
- **Match existing alerts back to feeds** per the stated algorithm — Notifications on `(group, condition category, conf.name)`, monitors on the `input` / `output` label filter — reporting unattributable alerts as such.
- **Set group scope per mechanism**: `group` on the Notification; `__worker_group` in the monitor's label filters, since `MonitorConf` has no group field.
- **Per-mechanism routing**: notification targets for connectivity, policy IDs for monitors, never one merged picker.
- State on the coverage summary that **Pack-scoped feeds are not covered**, so an incomplete table is not mistaken for a complete one.
- Discover Notification conditions and their JSON Schemas at runtime; generate connectivity forms from those schemas. Fall back to the verified `health.inputs` / `health.outputs` metric-monitor path (`health != 0`) where no matching condition exists.
- Discover Insights metric names and the per-feed dimension label at runtime.
- Single coverage table: name, type, group, direction, current health, a **separate error indicator** so a Green-with-error feed is visibly not fine, throughput sparkline, connectivity-alert and throughput-alert coverage columns.
- Filters for group, direction, "no alerts yet," "currently unhealthy," and "has an error."
- Detect a down monitor engine and warn before creating monitors.
- Multi-select rows plus a "select all uncovered" shortcut.
- Bulk-apply drawer: alert types, connectivity window and resolution notifications, throughput method (absolute floor as the default; percent-drop only once verified) and parameters, per-mechanism routing or opt-out.
- **Mandatory preview** listing every alert that will be created, its mechanism, and its exact condition or query — nothing created before explicit confirmation.
- Sequential `POST /notifications` and `POST /alert/monitors` with progress, honest per-item reporting, and retry of failures.
- Managed-alert registry and template defaults in KV, with reconciliation on load.
- Graceful degradation for each denied permission and for Insights being disabled or unhealthy.

**Nice-to-have (defer):**

- **Workflow 3 — per-alert tuning editor**, with threshold-versus-history and health-transition charts. Highest-value deferred item.
- **Workflow 4 — drift banner** surfacing newly added feeds with no alerts.
- **Workflow 5 — firing-history view** to spot noisy and suspiciously silent alerts.
- **Percent-drop-versus-baseline** as a throughput method, once a window-over-window form is verified (Verify First, item 2). Conceptually the best default; not shippable until proven.
- **Pack-scoped feed coverage** — `/p/{pack}/system/inputs|outputs`, `/p/{pack}/notifications`, `includePacks` on `GET /notifications`. Implementation Rule 12 shows these feeds carry real traffic and real health, making this the most substantive coverage gap on this list.
- Anomaly, forecast, outlier, and change monitor types as additional throughput methods — noting these are `AetosMonitorConf` on `/products/lakehouse_engine_metrics/monitors`, a different endpoint.
- Attributing monitors whose `query` is a PromQL string rather than a `MonitorQuery` object, which MVP reports as unattributable rather than parsing.
- **Alerting on `status.error` presence**, to close the Green-with-error blind spot. Needs a mechanism that can evaluate it server-side, which is why it is not in MVP.
- Persistent-queue depth and backpressure alerting from the `pq` data the status endpoints already return.
- Alerting on the per-type source metrics the discovery call already returns — `broken` / `activeBreakers` for TCP and Splunk, `numErrors` / `numDropped` for OTel — which are more specific connectivity signals than aggregate health.
- Distinguishing `Yellow` (degraded) from `Red` (critical) as separate severities rather than one `health != 0` state.
- Per-direction default templates (Sources tuned differently from Destinations).
- Suggested thresholds computed from each feed's own observed baseline.
- Bulk disable and bulk delete of app-managed alerts.
- Edge fleet coverage in addition to Stream worker groups.
- Export the generated alert set as config for review or version control.

**Out of scope:**

- **Evaluating alerts in the app.** Cribl's engines do this. Non-negotiable.
- **Defining a custom health model.** Consume the platform's `health` verdict as-is. Do not compute health from error counters, connection counts, or throughput — a second definition would disagree with the Cribl UI and erode trust in both.
- **Sending notifications.** The app attaches existing targets and policies; the platform delivers.
- **Creating or editing notification targets and policies.** Read-only; the admin manages routing in the Cribl UI.
- **Authoring new Notification conditions.** The app uses what `GET /conditions` reports.
- **Modifying Sources, Destinations, pipelines, or routes.**
- **Changing Insights settings.** If Insights is off, explain and link out rather than enabling it.
- **Replacing Cribl's alerting UI.** No general-purpose alert browser, no silence management, no triage or acknowledgement.
- **Root-cause analysis.** The app answers "did this feed stop or go unhealthy?", not "why."
- **Edge fleets, Search, Lake, and Lakehouse coverage** for MVP.
- **Pack-scoped Sources and Destinations** for MVP — disclosed in the UI as a stated limitation, never silently omitted (Implementation Rule 12).
- **Non-admin personas.**

## Edge Cases & Error Handling

Each capability fails independently; **never blank the page.** The two-mechanism split makes this notably robust — losing one engine does not cost the admin the other.

**Degrade by mechanism, not by intent.** Either intent can land on either engine — verified live, Source *throughput* is a Notification (`low-volume`) while Source *connectivity* is a monitor — so a reason phrased as "throughput is unaffected" can be false. Word each reason after the engine that failed, and name the directions it costs.

- **If user lacks permission — Notification write denied**: items routed to a monitor are still creatable; every Notification item is blocked with an inline reason. On the live catalogue that costs Destination connectivity *and* Source throughput.
- **If user lacks permission — Monitor write denied**: items routed to a Notification are still creatable. On the live catalogue that costs Source connectivity *and* Destination throughput.
- **If user lacks permission — both writes denied**: the coverage table still renders in full as a useful read-only coverage and health audit.
- **If user lacks permission — one worker group denied**: that group is skipped with a note; other groups render normally. One inaccessible group never fails the whole discovery pass.
- **If user lacks permission — status endpoints denied**: only the `healthCounts` breakdown on row expand reads "unavailable." The base health column is unaffected because it arrives inline with discovery. Connectivity creation is still offered — the condition evaluates health server-side whether or not the app can read it.
- **If user lacks permission — notification targets denied**: alerts still creatable with routing unset, stating that routing must be attached separately. Because monitor routing takes policy IDs from a source not yet identified, monitor routing may be unset even when targets *are* readable — the app names which of the two is unrouted rather than implying both are wired.
- **If data is unavailable — Insights denied, disabled, or unhealthy**: **only the monitor route is affected, because only it needs a discovered metric name.** Sparklines and the threshold preview are replaced with a short explanation. Connectivity via `unhealthy-dest` and throughput via `low-volume` both keep working — a volume-condition Notification must never be gated on Insights. Point at the setting; never render an empty chart with no explanation.
- **If data is unavailable — `GET /conditions` denied, or no matching condition exists**: fall back to the verified metric-monitor route for that intent and direction (`health != 0` for connectivity, a volume floor for throughput), labelled as such. **Never guess condition IDs.** An intent is only fully unavailable for a direction when its condition is missing *and* the monitor engine is down.
- **If data is unavailable — monitor engine (`aetos`) down, or `/alert/monitors` absent**: offer everything the condition catalogue covers, and block only the monitor items with the reason stated and the affected directions named. **Never report success for a monitor that cannot fire.** This is the live case on the verification org: `/alert/monitors` 404s and `aetos` reports no registered workers, so `low-volume` is the only working throughput route there.
- **If data is unavailable — a feed's metric never matches**: suspect the `type:id` join (Implementation Rules 3 and 9–11) before concluding the feed has no data. Show "no data" distinctly from "not covered," so a join bug cannot masquerade as a quiet feed.
- **If a discovered metric name returns no series**: say so and name the metric, rather than drawing an empty sparkline. Implementation Rule 8 shows this is a live hazard, not a hypothetical — two plausible-looking names silently matched nothing.
- **If a feed appears in metrics but not in config**: discard it. It is internal plumbing, a roll-up, or a Pack feed (Implementation Rules 10–12) — never invent a table row from a metric series.
- **If an action fails — partial bulk failure**: expected, and must not be hidden. Report per-item outcomes honestly, keep failed items selected, and let the admin retry without reconfiguring. **Do not swallow errors.**
- **If an action fails — a write is rejected mid-sequence**: continue the remaining items rather than aborting the batch, then report the full outcome.
- **Requests time out after 30 seconds** at the platform proxy. Use `AbortController` for anything the user can navigate away from.

**Write safety (from `AGENTS.md`, non-negotiable):**

- Creation happens only after the admin confirms the explicit preview. **Never create on render, mount, or a timer.**
- Updates and deletes apply only to app-managed alerts, behind a confirmation naming the object and stating when the action cannot be undone.
- Every volatile operation requires a deliberate button click and reports its outcome.

**Storage safety:** never `localStorage`, `sessionStorage`, `IndexedDB`, or cookies. The sandboxed iframe makes browser storage unreliable — it can be partitioned, cleared, or blocked, and is never shared across users, devices, or sessions.
